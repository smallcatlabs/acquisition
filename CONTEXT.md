# Acquisition (Rust rewrite) — Agent Context

This doc is working memory for coding agents and a place for developers to inspect and tweak things, not a spec or requirements document. It records what's settled, what's open, and what must never happen. Terse on purpose. Current state only: superseded content is edited or deleted in place — git holds the history. Facts about GGG live in `docs/design/network-ground-truth.md` and are cited here by number, not restated. Decisions are a numbered registry (`C<n>`, below): the ruling and its rationale live here, one bullet each; the mechanism a decision implies lives as a doc comment on the code that implements it and in the tests that pin it, cited by id. Where code exists, code is the source of truth for implemented shape — this doc holds boundaries, properties, and open questions, never a parallel description of what the code already says.

## Orientation (3 sentences)

Acquisition is a Path of Exile inventory-management tool being rewritten from C++/Qt to Rust under the same GGG OAuth registration as the existing app. The system is a local daemon that owns all GGG API traffic, with thin frontends that share it: a CLI, an MCP server, a TUI, and a GUI to come. The GGG relationship (OAuth registration, rate-limit standing) is the project's most valuable asset and every design decision defers to protecting it.

## Invariants

As few as possible, each as simple as possible: properties, not mechanisms. An invariant enforced wholly inside one component doesn't need to be listed here unless there's a good reason.

1. **Every daemon-originated request to GGG goes through one rate-limit choke point and one send-lifetime global gate — API GET, HEAD probe, OAuth code exchange, and OAuth refresh** (the token endpoint has its own rate-limit policy: ground-truth N33). The browser-owned authorize navigation is outside this boundary; the daemon opens the URL and does not send that request. A daemon HTTP path that bypasses the choke point or gate is a critical bug regardless of how reasonable it looks locally.
2. **Rate-limit headers from GGG (`X-Rate-Limit-*`) are the source of truth.** Local rate-limit state is a prediction; headers correct it.
3. **Never retry through a Cloudflare block.** Recognition signatures and the one known incident: ground-truth N1–N4, N28.
4. **The user-agent string stays continuous with the existing registration** ("Acquisition 1.0, same registration, new capabilities" framing with GGG).
5. **Refresh tokens are never stored in plaintext on disk.** The OS keyring is their default home.

## Decisions — the registry

One entry per decision: a stable id (`C<n>`, never reused; a superseded decision is rewritten in place under its id, or deleted), the ruling in plain declaratives, one *Why:*, and one *Pinned:* naming the file and the test that hold it (`nothing yet` when nothing does), with a short gloss on every id it cites. An entry carries no history (no date, no commit, no quote, no "Amended" or "Decided"): `git log -S'C<n>'` and the commit messages hold it, and `tools/docs-check.sh` refuses the markers. A ruling whose build waits says `Unbuilt` and names its issue. An entry is one bullet under `tools/docs-check.sh`'s length limit; a decision that needs more is a decision plus a mechanism, and the mechanism goes to the code. The limit is a prompt to route, never a test of meaning: an entry that overflows usually carries mechanism, one that lands on the limit is usually two decisions, and one that enumerates grows per item and belongs in the tool that enforces it (C1); what moves out keeps its authority where it lands, in a labelled contract-detail section the entry cites. Tests and docs cite decisions by id; the check refuses an id that does not exist and reports a decision nothing cites.

Only the **cross-cutting** decisions are here, because an agent must know them before it knows which area it is in; the check caps their count. Every other decision lives in its area's file with what that area has parked, read before touching that area (`AGENTS.md`, "Read before changing anything"), and named again at the top of the module it governs:

### Cross-cutting

- **C1 — The workspace is library-centric and the daemon is its own artifact.** `acqd` is the only GGG sender and links the protocol crate and the store, nothing else; the store links none of the workspace crates; the protocol crate links serde alone; a frontend links client, protocol, store, planner and search as it needs them, never the daemon; neither the daemon nor the planner links the search. *Why:* shared logic is written and tested once, and the edges are refused by a check, not held by discipline. *Pinned:* `tools/docs-check.sh` (the edges).
- **C2 — The daemon owns shared state; clients talk to it over local IPC.** *Why:* invariant 1 becomes structural. *Pinned:* nothing yet.
- **C4 — API requests are jobs, not calls.** A job has an id, a state and a priority. *Why:* a rate-limit wait can reach 300 s, which a blocking call cannot represent across three frontends. *Pinned:* nothing yet.
- **C12 — A frontend consumes exactly two surfaces: the daemon protocol and the store's read API.** A third channel is a protocol or store change, ruled first. *Why:* the contract stays in two places, enforced by what a frontend links. *Pinned:* `acquisition-protocol/tests/wire.rs`.
- **C14 — Agent traffic against GGG is allowed; the daemon is the single gate.** *Why:* GGG permits agent use that respects the API rules, and one gate every client passes through is the only enforceable line. *Pinned:* `acquisition-mcp/tests/ggg_refusal.rs`.
- **C15 — Tokio and reqwest.** Core exposes `async fn`; frontends provide the runtime. *Why:* the ecosystem default; a core with no runtime lets each frontend own its own. *Pinned:* nothing yet.
- **C34 — Four layers, each with one authoritative mutation path: facts through the store's ingest, intent through its annotation API, derivations reproducible from declared inputs, effects through the daemon.** The daemon is blind to intent and creates work only in service of client-submitted work: no schedules, no policy execution. *Why:* a sync can never clobber intent, structurally. *Pinned:* `tools/docs-check.sh` (the daemon, the protocol and the client never name the intent API).
- **C35 — Annotations are the only irreplaceable local state.** One per-account file named by the account uuid, keyed on stable GGG ids, written only through the store crate under revision compare-and-swap; no fact-side event deletes intent; backup is a store-managed snapshot. *Why:* facts are refetchable; intent has no server to refetch from. *Pinned:* the `c35_` tests in `annotations.rs`.
- **C38 — A plan is a serializable, immutable authorization envelope, and plans are binding.** Applying executes exactly the listed actions or a subset, never an addition; new facts produce a new plan. *Why:* reviewed work stays exact. *Pinned:* `acquisition-cli/tests/apply_loop.rs`, `acquisition-cli/tests/plan_json.rs`.
- **C46 — Shared semantics live in Rust, and every frontend is a Rust adapter** (clap, `rmcp`, a webview whose Rust backend is the adapter). A surface that evaluates for itself is a second semantics, ruled first. *Why:* this is what makes "built once, inherited by every frontend" true. *Pinned:* `acquisition-mcp/tests/pricing_tools.rs` (the tools call the functions the CLI calls).
- **C47 — Panics are for broken internal invariants only; malformed external input is a structured error with a stable kind.** The store, plan and protocol crates deny `unwrap` and `expect` in production code. *Why:* a persisted queue turns a reproducible panic on bad input into a crash loop. *Pinned:* the `unwrap_used` lints in the store, plan, protocol and search crates' `lib.rs`.
- **C48 — The SQLite schema is internal; raw SQL is not a surface, and there is no cached search service.** *Why:* a stale result taken for current truth is the failure a cache reintroduces. *Pinned:* nothing yet.
- **C79 — Surfaces GGG does not sanction (the trade site, the forums, third-party feeds) are governed inputs, never runtime dependencies, and permission attaches to the access method.** The daemon never touches them; nothing at runtime depends on one; `SURFACES.md` registers each; a human may read one, and tooling fetches one only with the permission its row records. *Why:* the relationship is protected by keeping such surfaces deliberate. *Pinned:* nothing yet.
- **C110 — The Rust workspace is MIT OR Apache-2.0, and nothing in it derives from the expression in a C++ file whose copyright header names anyone but the owner.** The C++ app's behaviour and GGG's facts may be read and distilled, cited by claim or `acquisition-qt@<hash>`, never transcribed; no lint compares the trees until the next Rust table is drafted from a C++ one. *Why:* the C++ tree has many authors and the Rust tree must stay relicensable by one. *Pinned:* nothing yet.
- **C120 — Acquisition never posts to the forum or the shop.** `shop render` writes pages to stdout and a human pastes them; outward credentialed traffic (POESESSID) is refused, not deferred. *Why:* the owner's ruling; a user's agent can drive the user's own browser. *Pinned:* nothing yet.

## Parked (cross-cutting only; do not build yet)

Scope deferred with its trigger, so deferral never needs re-arguing: something someone would propose and the project has decided not to make yet. A trigger nobody could observe is rot (accepted by the owner 2026-10-12). An area's parked items and open questions live in its `decisions/<area>.md` under "Parked", read before touching the area; only what crosses every area is here. An entry is deleted in the commit that builds it, never because its trigger fired; one whose trigger has fired and that nothing has built yet stays and names the step or slice that builds it. A trigger names evidence, never a point in the sequence; a step of the sequence note schedules a park by pointing at it, and the park keeps its trigger. An entry is the item, where it lands, and the trigger that reopens it, with at most one clause of why; a workaround is a README known gap, history is git.

## Working style

The charter: the work finds out what the system needs to be and pins that as tests at its boundaries and as recorded rulings, so the code stays replaceable given a reason; the rate limiter and the single gate are the proven foundation, so every later caller, human or agent, is regulated by construction and never a fresh risk. The code ships (owner, 2026-10-11; ADR 0003 in `acquisition-qt` is his record): "The Rust build ships as Acquisition's agent surface by PoE2 1.0: the CLI, the MCP server and the daemon on Windows, macOS and Linux; GUI and other features follow." The order of the slices to that release was `brainstorming-notes/36-the-road-to-the-agent-release.md`; the work after it is `roadmap/README.md`. Who holds which boundary is `AGENTS.md`. The numbered principles are cited by the registry as `P<n>`.

- Tests pin behavior at boundaries, never mechanisms. A test that reaches into daemon internals pins this implementation, not the contract, and is disposable. The GGG-side contract surface is the send journal (`TESTING-NOTES.md`); the frontend-side surface is the protocol, pinned under C85.
- Rulings first, findings after (owner, 2026-10-13, verbatim: "rulings first, findings after"). A ruling — an invariant, a boundary, a registry entry — is brought to the owner and recorded in the registry before the code that depends on it; "design" means updating the registry, not writing a spec. A finding — what building or running taught — is recorded after, at its home (`AGENTS.md`, "Routing"). When the current internals get in the way of learning, record the finding and move on rather than polishing.
- Prefer simplicity over flexibility when trade-offs arise. Prefer idiomatic Rust patterns over translations from Qt/C++.
- **P1.** Deep design sessions are evidence-driven, never calendar-driven; crystallize before building. Rulings land in the registry; session notes (`brainstorming-notes/`) are disposable history, never a second authority.
- **P2.** In product scope the validating consumer is real use, and each frontend contract needs its own — the owner's live use validates a CLI slice, not the GUI/MCP/TUI contracts; friction notes are data the way the send journal is data.
- **P3.** Generalize after two materially different consumers reveal the shared property — except where an early choice controls irreversible identity, durability, safety, or compatibility (those get first-consumer treatment; the uuid identity decision is the example).
- **P4.** Tactical taste is settled by a lint where mechanical and a recorded property where stakes are real — design discussion precedes a property's promotion to lint or test; everything else is agent-owned internals.
- **P5.** Structure over discipline: a rule that can be broken silently becomes a dependency edge, a lint or a test; knowledge sits at the lowest rung that holds it — structure, test, script, on-demand file, always-loaded file, history — and a boundary never sits below the always-loaded rung.
- **P6.** Ceremony is earned by evidence and retired by it: a procedure becomes a skill after it has run twice and repeated a trap; a generalization waits for two consumers (P3); a check, a rung or a rule is removed when what it guarded is proven.
