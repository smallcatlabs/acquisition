scope has run after round 5c on the same workflow as the baseline,

baseline (the same mutant at the same or a drifted line, a listed

## Do

1. **The comparison.** A script under `tools/` (or a `#[test]`-free
   Python script run with `-I`, the worker's call, kept under
   `tools/` and named in the report) reads both runs' `outcomes.json`
   and lists every mutant missed after, keyed by file, function and
   the mutation's text (never the line), against the baseline's: the
   same mutant missed in both (a baseline survivor), a mutant listed
   in `mutants.toml` at a line that drifted (the listed pattern
   matches but for the line), or a mutant missed after and not before
   (a survivor t5 introduced). The report carries the three lists.
2. **The twelve listed lines** are read again, each: the tie still
   leaves the limiter in the same state with nothing carried forward
   (the config's rule), and its line is updated to the line it stands
   at; a listed mutant whose reason no longer holds is pinned instead
   (the tie rule's boundary row).
3. **The six `policy.rs` survivors** are pinned in `spec.rs`, by one
   rule: a word a user meets is pinned by the test that reads the
   word. A `Client` rule labelled "Client" (`rule_label`); a rule
   capitalised from its lower-case form ("ip" to "Ip", the first
   letter only); `rate_words` with `restricted_secs` 0 carrying no
   "restricted" and with 1 carrying ", restricted 1s" (the tie at
   zero decides a word, so it is pinned, not listed). Each pin is seen
   to kill its mutant by `cargo mutants --re 'rule_label|capitalise|
   rate_words'` (a run over those functions only), its output in the
   report.
4. **A survivor t5 introduced** (the third list of Do 1), if any: each
   pinned at the lowest crate that holds it, or listed with its reason
   under the config's rule, named in the report; none is left
   unexplained.
5. **The counts.** The daemon's `#[tokio::test]` and `#[test]` per
   file at `a4834369` and at 5c's close (printed commands); the door's
   tables, rows and scenarios at 5c's close (the rounds' ledger rows
   summed, re-counted by a printed command); the gate's test stage at
   round 1's input and at 5c's close, from the ledger; all in the
   report and the close's ledger row.
6. `tools/gate.sh` on the tree; one commit for the config's lines and
   the pins (two if the comparison script is its own).
