Orchestrated by Fable 5.1 the evening after v1.0.0-alpha.1 shipped. Seven read-only audits (four Opus, three Sonnet) plus the orchestrator's own measurements. Nothing in the repo was changed. The synthesis is first; the seven reports follow verbatim as the evidence.

## Synthesis (see the terminal message of the session for the prioritised version)

Amended 2026-10-19 after the outside review of the roadmap commit (`roadmap/reviews/roadmap-a987d02f.md`, finding 10): five sentences below had grown wider than the reports they summarise and are corrected in place; nothing else in this file changes.

1. The core is sound; the weight is in the shell. Production logic is ~45k lines, dependencies are lean and justified, zero TODOs, essentially no dead code (report 1: "almost none"), nothing the audits read bypasses the invariants (no audit tested them), the network area is the best-kept. The weight is prose (17k comment lines in src, 450 KB root markdown, 375 KB notes), tests (72k lines, 1.6:1 against production) and three un-split giant units (daemon.rs 9.9k, ratelimit.rs 4.5k, execute_inner 600 lines).
2. The governance framework was tuned for the phase that ended on 2026-10-19 (unshipped, single owner, agents as the only readers, the main risk being re-argued or clobbered decisions). The next phase's risks are different: users, game changes, a GUI, speed. P6 says ceremony is retired by evidence; almost nothing has been (TESTING-NOTES records one retired checker and its procedure). 43% of commits are docs-only; about 68 commit subjects mention routing, budgets or the checkers; 38 of 119 registry entries sit in the last 50 bytes of an 800-byte limit; the checkers verify pointers, not truth (a skill contradicts C116; AGENTS makes a false claim about four crates; the ground-truth header is stale).
3. Parks have become an issue tracker in prose. 106 items, +26 in the last three days; 40 of the triggers are "a user" or "a future run" which only an intake channel can fire. Six have fired on the project's strict rule (ST-3 added at the review); ~20 are near-fires from the seats. The external-tracker park's own trigger ("the first issue a park cannot absorb") has not fired; the argument for firing it by ruling is that 14 user-report triggers can fire only through an issue.
4. The keystone refactor is one move that three audits converged on from different directions: the refresh/apply orchestration (and account resolution, store opening, error vocabulary) is duplicated between CLI and MCP and has already drifted. Extracting it into a shared function layer (a) makes C46 true everywhere, (b) makes the triple-pinning of semantics across search/CLI/MCP tests structurally unnecessary, (c) is the GUI's foundation.
5. Performance: the corpus reload sits 1–28 ms under its 500 ms budget by measurement, but the measurement copy has 6 removed items and real stores accumulate tens of thousands; store age alone doubled the ask (0.47 → 0.98 s at 90k removed) via a quadratic loop and an index that cannot skip removed rows. Every reader takes the write lock on open. acq-mcp reloads the whole corpus on every call although C98 allows it to hold one.
6. Tests: the owner's instinct is half right. E2E through real binaries exists (apply_loop, characters_wire, plan_loop, release-smoke). The excess is ~45 tests pinning one behaviour at three layers, seven copies of the process harness, ~430 prose-literal assertions, and 70 separately linked binaries. No journey over fetched data exists because the mock's items are too thin.
7. Game release: every game table is frozen at 3.29.3.3 and site captures of 2026-09-12; nothing in the repo or the gate tells anyone what changed. PoE2 day one is small if GGG ships a stash endpoint (one route row, a first contact, test edits) and nothing otherwise; the per-realm policy merge is a data-loss gotcha with a December deadline.
8. GUI: thin rulings (C16 Tauri, undated, unscoped). The protocol and read API already give a minimal GUI what it needs; the twelve GUI-triggered parks are polish. The recommended first shape is a loopback web UI on the same function layer the MCP uses, with Tauri as a later wrapper; it is the shape where a human and an agent look at the same answers.
9. The prose style is the framework's fingerprint: possessive chains plus bare ids, written for a writer who holds the context. The project measured the same cost on its blind seat agents and banned ids from user text (C116); the developer agent is in nearly the same position outside the area it just read.

**Accidental complexity (impression from reading, not proven).**
- *Locks.* `Daemon` holds 5 std Mutexes (`shared`, `log`, `store`, `jobs_db`, `queue_failure`). ChokePoint has 2 (`limiter`, `sends`), gate 1, rails 2.
  - All are sync and short-held. I saw no lock held across `.await` in what I read.
  - The ordering is nested: `persist` logs while holding `shared` (doc at :1029-1030). There is no documented lock order, which is the main latent risk.
  - `queue_failure` and `jobs_db` could fold into one `Mutex<Queue>`.
  - `store` could plausibly live in `Shared`.
  - Net: one or two fewer locks. That is modest, not a redesign.
- *Concurrency.* The dispatcher (one task per scheduling key, plus the gate's 2-send bound and the limiter waits) is three layers. Each answers a different ruling (ordering vs. Cloudflare bound vs. GGG headers) and each is justified in its doc. I would not collapse it.
- *Token refresh.* The single-flight refresh (watch channel, RefreshOwnerGuard, generations, `SESSION_CHANGED_DURING_REFRESH`) is the most intricate part. It is heavily pinned by `auth_session_tests`. Leave it alone.
- *What actually costs something.* The real accidental complexity is the string-typed kind/params (section 2c), not the state machines.

# Report 2: Test suite (Opus)

### Short answer
Half right. The suite is **not** missing end-to-end tests. Several process-level tests already drive the real `acq` and `acqd` binaries through a scripted mock login, plan and apply, store ingest, and output. The suite also has a disciplined core (the daemon, the protocol, the client contract, the search crate's boundary tests) that is better than "overdone". Where the owner is right is **cross-layer duplication and hand-written prose literals**. Most of it is in the search/CLI/MCP triangle, which grew one test per seat finding per surface. There is also no single *journey* test (login → refresh → tabs → search → price → shop on fetched data), and the mock provider's items are too thin to support one. ### 5. Complexity cost for an agent

- **Seven copies of the process harness.** `cli/tests/harness`, `mcp/tests/harness`, `contract.rs`'s own, and private copies of `command`/`http_get`/`login`/`sole_json` in `apply_loop.rs`, `characters_wire.rs`, `daemon_stop_checkpoint.rs` and `realm_wire.rs`. Eight CLI files carry their own `sole_json`. `place_link`/`same_file` are duplicated in the MCP harness and contract.rs. The env-scrub lists differ: `apply_loop.rs:41` removes `ACQ_JOURNAL`/`ACQ_IDLE_SHUTDOWN`, while the harness sets them. A new `ACQ_*` knob has to be scrubbed in up to seven places.
- **Prose literals are the main brittleness.** There are about 368 `contains`/`starts_with`/`==` string matches in CLI tests and 62 in MCP tests, many on long sentences (seat_faults.rs:1437, :1293–1299; search_tools.rs:1661). A wording change fails tests in 2–3 files. An agent fixing them learns nothing, and is tempted to loosen the match.
- **Stale doc comment (verified).** `cli/tests/seat_faults.rs:2114–2119`, above `the_locations_view_is_gone_since_tabs_is_the_list`, is a copy of the C118 fetch-age comment at :1556–1559 and describes a different test.
- **Generated search (`common/generated.rs`, 2,840 lines) is heavy but well-founded.** Its properties are metamorphic: the oracle is self-consistency, not a second implementation (generated_equivalence.rs, generated_completion.rs headers). Per 3f13b7a9 they found real faults. The cost is reading time, not trust.
- **Test names are good failure messages.** They are sentences of the property with the decision id, and failures print the whole output (`"{shown}"`). That is agent-friendly. The friction is finding *which* of three layers is the one to change.

### 6. Speed (reasoned from code; the orchestrator's timing is authoritative)

- **Already done.** `ACQ_CASES` local/full split (3f13b7a9): generated binaries went from 88 s to 15.5 s locally, and the gate's test binaries from 175 s to 105 s.
- **Process spawns.**
  - `search_json.rs`: about 152 `acq` spawns. With ~50 MB debug binaries each spawn is mostly exec and dynamic load; measured 16 s at 2026-10-12.
  - `seat_faults.rs`: about 144 spawns plus 12 daemons.
- **Daemon start cost (likely lever, unverified).** Every `acqd` start hashes its own 27 MB debug executable (`daemon.rs:4681` `artifact::of_current_exe()`) with unoptimised `sha2`. `Cargo.toml` `[profile.dev]` has no per-package opt-level. Adding `[profile.dev.package.sha2] opt-level = 3` is one line and could save a large fraction of a second per daemon start, across dozens of starts. Measure first.
- **Serial by design.** `contract.rs` runs under one lock (process-wide env) and includes a ≥5 s deadline test. `watch_recovery`/`plan_loop` poll up to 30–60 s deadlines, but these are deadlines, not fixed sleeps. Polling is everywhere; I found no bare fixed sleeps.
- **Link time.** 70 integration binaries each link search, store, plan, rusqlite, serde and so on. Consolidating to one binary per crate (`tests/it/main.rs` + `mod`s) is a well-known build-time lever. Keep `contract.rs` and env-mutating files separate.
- **cargo-nextest.** A process per test lets the 9 contract tests and the slow CLI files run in parallel across binaries. Under nextest the `ONE_AT_A_TIME` lock becomes moot. The CI workflows use plain `cargo test` (verified, gate-linux.yml:75, gate-windows.yml:56).

# Report 5: Performance (Opus)

Scratch: `w1` a `.backup` copy of the M3 store; `w5` adds four synthetic copies of every item; `w6` adds 90,914 synthetic removed items; `ask.sh`, `ri.py` timing scripts. Timed `target/release/acq` (built Oct 18) and `target/debug/acq` with `/usr/bin/time`, profiled with macOS `sample`. Every run used `ACQ_PROVIDER=mock`, `ACQ_NO_SPAWN=1` and a scratch `ACQ_STORE_DIR`. No daemon started, no cargo.

### 1. The hot paths as built

**CLI startup** (measured): `acq --version` under 10 ms; `--describe` 40 ms and 62 MB. Not the problem. Keyring setup happens only in the daemon. Reference TOMLs parse lazily; the 2 MB trade tables only on a trade query.

**`acq search` over a whole league.** The corpus is re-derived from JSON on every query, as C98 designs it. Each ask: opens the store; one `read_corpus_of` transaction (header, `gone` list, every live body streamed and parsed into `serde_json::Value`, derived, classified, categorised; `search/src/corpus.rs:589-800`); `price::join` (`corpus.rs:796`): one `pricing_snapshot` plus one `listing::resolve` per league in the realm, each snapshot re-reading every item row and running `json_extract(i.json,'$.note','$.inventoryId')` over every body (`store/src/snapshot.rs:654-705`); `still_at`, re-reading the whole corpus up to 3 times if facts or intent moved.

Measured on the M3 copy (22,623 live pc items, 3,444 tabs, 29.9 MB of bodies):

| Build / store | Wall time | Peak memory |
| --- | --- | --- |
| Release, empty query | 0.46–0.49 s (8.35 G instructions) | 228 MB |
| Debug, empty query | 2.62–2.65 s | — |
| Release, 5× store (113,635 items) | 2.16–2.33 s | 971 MB |

**Daemon** (reasoned): throughput bounded by GGG deliberately; limiter wakes at most once a second while holding; ingest synchronous on a tokio worker under a std Mutex (fine at GGG's pace). `acq … --wait` polls every 500 ms plus a progress request (`cli/src/main.rs:1978-2010`); `jobs --watch` every 1 s (`:2421`).

**Ingest** (reasoned, `store/src/lib.rs:2273-2420`): per item a non-cached SELECT, full parse of old JSON, `same_item`, an UPDATE rewriting the whole row even when unchanged, event inserts; `prepare_cached` never used. Matters only for `store import`.

**Store open** (`store/src/lib.rs:788-951`): every `Store::open` takes an IMMEDIATE transaction (the write lock) just to read `user_version`, including pure readers. A reader waits behind any ingest transaction and briefly blocks the daemon. The annotations file does it right (`annotations.rs:606-640`, deferred read first).

### 2. Removed items make the live ask slower

Measured: 90,914 removed items (live unchanged) took the live empty query from 0.47 s to 0.98 s.
- **A quadratic loop.** `corpus.rs:735`, `let live = locations.iter().any(|l| l.id == *id);` once per gone id over every live location: 90k × 3.4k. ~130 samples self time. `header.gone` holds every removed item ever (`store/src/corpus.rs:419`). The schema comment says "the removed are few beside the live"; over a league that stops holding.
- **Index scans touch removed rows.** `items_location (location_kind, location_id)` cannot filter on `removed_at`; `read_items` went 77 → 109 ms. A partial index `WHERE removed_at IS NULL` brought it back to 72 ms.

Per-league cost: `read_items` for an empty league still takes 7 ms; the owner's pc realm names 7 leagues, ~35 ms per search on leagues holding nothing.

# Report 7: GUI readiness (Sonnet)

## 1. What is ruled
- **C16**: "Tauri for GUI (webview frontend). Why: item search/grid/filter UIs are a strength of web tech; egui considered and passed on for data-heavy views." No date, no pinned test, no scope.
- **C46**: shared semantics in Rust; every frontend a Rust adapter; "the webview is presentation, never a second implementation".
- **C12**: two surfaces only. **C2/C4/C8**: daemon owns state, requests are jobs, subscribe/event channel "from the start" (C8's Why names "GUI push updates"). **C1**: a frontend never links the daemon.
- daemon.md park: a GUI-hosted daemon refused; the GUI spawns `acqd` like the CLI; the GUI slice must record its spawn policy.
- **C10**: three doors (Use, Observe, Stop); in real mode a use door spawns only with a terminal on stderr (C88). A GUI has no tty: a real design question in `client.rs`.
- **C104**: "a client that holds a tree (a GUI's rows) may send it, and every answer carries both." The query tree is the form model.
- Note 36: "whether Tauri is revisited is that slice's first question." `tools/docs-check-breakers.sh` has an edge check that fails the day a frontend gains a library target (a Tauri crate will trip it).
- Not ruled: the framework (Tauri is a default), webview vs browser page, who serves it, item images, packaging, the spawn policy. P2: the GUI needs its own validating consumer.

## 4. Risk to C46
Sorting/grouping are in the language; rows page via `next`; selection and form state are C104's tree (keep it opaque, mutated only through a Rust command); no incremental updates in v1 (refetch on invalidation); new semantics live in search/plan, never the GUI crate. The MCP's 25 tools are a ready-made API; the GUI backend calls the same Rust functions. The real risk is process lifetime: a long-lived GUI holds a corpus, so staleness and reload become central.

## 5. Recommendation
First slice: **B**, built on a shared function layer the MCP also uses, Tauri deferred as a wrapper. Pre-work in order: (1) extract the MCP's tool bodies into a shared Rust function layer returning typed values; (2) fire "a watch that waits for the daemon to return" as a client-crate subscriber with reconnect; (3) record the spawn policy and extend `ConnectOptions` for a no-tty human frontend (C88); (4) sticky realm/league as a GUI-held control; (5) rule item images in or out of v1; (6) measure the full-projection reload at real store sizes; (7) leave parked: correlation ids, results over a subtree, error taxonomy, queue drag-and-drop, Dashboard reshape (the first GUI produces their evidence, P2). Size: ~1 week extraction + subscriber; 1.5–2 weeks API + web views; ~1 week hardening; Tauri packaging 1–2 weeks on top. About 4–5 weeks for B's alpha, 5–7 for A.
