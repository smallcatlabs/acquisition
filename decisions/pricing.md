# Decisions — Pricing: intent values, listing, reference data, plans, import, render

Part of the decision registry (`AGENTS.md`, "Cross-cutting rulings"): the rulings that bind the `buyout` intent kind and its target, intent provenance and typed values, the listing state and its inheritance, the currency reference table, `PricePlan` with its receipts and revert, the legacy import, and `shop render` (the pricing module of `acquisition-plan`, `acquisition-store/src/annotations.rs`, the reference table beside its consumer — built by the pricing slice, `PRICING-SLICE.md`, "Step ledger"). Read this before touching that code; the cross-cutting decisions (C79, governed surfaces, among them) and the invariants are in `AGENTS.md` and are always loaded. Same rules as there: one entry per ruling, in the form `tools/bothy.py`'s docstring states; the mechanism lives in the code's doc comments under the id.

Three rulings (C71, C73, C78) are unbuilt and keep their ids as direction, so citations stay valid. Under C79 the first registered surface is the trade site, access method `browser`, no automated fetch; the register is `SURFACES.md`.

## Pricing

- **C64 — Pricing is intent edited offline: manual listing intent is stored as explicit assertions only, and game pricing, inheritance and every listing state are derived.** A `buyout` row sits on an item, a tab, a substash or a character; inherit is the absence of a row, never a value; a price seen in a tab name or an item note is derived from a fact, never a row; an item's listing is recomputed on read. No pricing operation contacts the daemon, quotes or creates a job. *Why:* a derivation cannot be clobbered (C34, four layers), where materialized inherited prices needed locks against refresh. *Pinned:* `acquisition-cli/tests/price_story.rs`.
- **C65 — Every intent write carries structured provenance: the channel it came through (`written_via`) and an optional claimed `actor`.** Both are stored on the row and returned on every read; the write API requires `written_via`; `actor` is untrusted audit metadata, never identity or authorization. An intent file below annotations v3 is refused, never migrated. *Why:* who set a price and through what cannot be reconstructed later, and agents write intent (C14, agent traffic allowed). *Pinned:* the `c65_` tests in `annotations.rs`.
- **C66 — Intent values are typed at the write API: a kind declares its schema version and a strict parser, a value that does not parse under its stamp never lands, and a current-schema value re-serializes to exactly what was read.** The generic part (version gate, unknown fields refused, exact round trip, compare-and-swap) lives in the store crate over a per-kind trait; a kind's shape stays its owner's; an older value upgrades in memory and stays stored as written. A kind may refuse as a new write what it reads (`check_write`), at the door, never on a read. *Why:* a shape change after data exists would migrate the irreplaceable state. *Pinned:* the `c66_` tests in `annotations.rs` and `acquisition-plan/src/lib.rs`.
- **C67 — The v1 `buyout` and its target.** A typed `PriceTarget` is the public API: item and character by id (C55, the id is identity), tab by `(realm, id)`, substash by `(realm, parent, id)`, league-less. `type` is `exact` (`~price`), `negotiable` (`~b/o`), `no_price` or `skip` (`~skip`); the first two carry `amount` and a `currency` tag that must resolve in the reference table (C68, reviewed reference data). `amount` is a decimal of at most four fractional digits, or a lot ratio `wanted/lot` of two unreduced positive integers (T2, ratio listings), in canonical text. *Why:* the key mirrors the store's identity, and widening is compatible where narrowing is not. *Pinned:* the `c67_` tests in `price.rs`.
- **C68 — Reference data is a fifth input: a versioned, reviewed, committed table whose rows cite evidence, shipped inside the binary, read-only, never in a store file, enumerable by every surface, cited by version when used.** A tool may propose rows from a governed source (C79, governed surfaces); a human commits. The currency table is first: the immutable `tag` intent cites; `emit`, the word GGG's client writes into a note; `aliases`, each cited. A tag is never removed or reused; a dropped currency keeps its row, marked; additions are reported. *Why:* it is not a fact, not intent and not a derivation, and a list without evidence rots. *Pinned:* the `c68_` tests.
- **C69 — A listing is two independent resolutions, their relation, and the effective price (C81, the most specific statement).** The manual side resolves by rules (C70, tab coverage); the game side reads the note, then the tab name, as a price (exact, negotiable or a ratio) or `skip`; any other text has no effect, is shown as written, and the tab applies (T11, priced by tab name). The relation is manual-only, game-only, agree, conflict or none. Each result carries both sides with causes, revisions, basis, versions and the raw texts. *Why:* four statements fused into one need locks; the site's display states are not modelled. *Pinned:* the `c69_` tests (the parse), the `c81_` tests (the effective price).
- **C70 — A priced tab covers that tab and its children, as a policy id does (C37, a tab covers its children).** A substash row overrides its parent's for that substash; an item row overrides both; a character row covers its items. Coverage is the manual side's inheritance only and says nothing of eligibility (C74, the shop render). *Why:* tab-scoped intent should have one shape for both kinds. *Pinned:* the `c70_` tests in `listing.rs`.
- **C71 — A `PricePlan` compiles a desired state against a named snapshot and is applied atomically to the intent file; its preconditions protect intent, and fact drift is reported, never a gate.** Unbuilt: issue #48. Until it is built a price is a single-row write through the annotations compare-and-swap, and a cited currency tag must resolve at write (C67, the buyout). *Why:* "what was reviewed is what lands" (C38, binding plans) holds for one row through compare-and-swap; a batch is what needs a plan. *Pinned:* nothing yet.
- **C72 — Pricing never edits the sync policy, and a price never locks a tab into refresh.** The relation between the two kinds of intent is reported, not enforced: the consumer that needs freshness, `shop render` first, names priced locations outside the policy's coverage, priced facts older than its window, and items moved or reindexed since the render's basis, each with its remedy (the policy edit, or the `RefreshPlan` it would take; C41, reads observe). *Why:* "priced tabs are always refreshed" is one kind of intent silently rewriting another; a report keeps the policy what its author wrote. *Pinned:* the `c72_` tests in `shop.rs`.
- **C73 — The legacy import is a source of desired state for the one compiler (C71, the price plan), read from the 0.18 userstore under one consistent snapshot, with every source row accounted for in the reviewed plan.** Manual rows are the desired state; inherited, game, auto and `~c/o` rows are non-actions; an existing row is never overwritten; the realm is explicit; the file's username binds to a uuid with stated evidence, only a contradiction refusing. Unbuilt: not doing until the owner rules the replace. *Why:* the import dissolves into the plan and apply path instead of a wizard of its own. *Pinned:* nothing yet.
- **C74 — `shop render` is a derivation, publishing is out of scope, and every item the page omits is counted with a named reason.** The page is a pure function of facts, intent, reference data, a template and a ruled policy; it is written to stdout in pages labelled *n* of *N*; it sends nothing (C120, no posting); the template is an input, not stored. What the game already lists (C81, the effective price) is omitted and counted, an unruled cell is blocked, and a prior post is never read (T6, posts not reported back). The policy's rows cite trade claims and observations, never the render's own output. *Why:* every human surface is a derivation over a machine surface. *Pinned:* the `c74_` tests in `shop.rs` and `price_story.rs`.
- **C75 — Pricing lives in `acquisition-plan` as a module; `PricePlan` is built operation-specific, and what the two plan-bearing consumers share is recorded after it exists, not presumed.** The hypothesis: the shared thing is the compile, review, apply loop and an envelope discipline (stamp, strict round-trip parse, provider and uuid, basis, precondition set, non-actions, counts), not the action vocabulary or the apply target. A crate split waits for a dependency-graph property it would buy. *Why:* generalize after two consumers reveal the shared property (P3, two consumers first). *Pinned:* nothing yet.
- **C78 — Every applied price plan leaves an intent receipt in the same transaction, from which a conditional inverse can be compiled.** A receipt holds the plan's hash (`applied_plan`), when and through what it was applied, its origin, its counts, and each mutation with prior and written values; `revert` compiles a new plan against current revisions and refuses whole if any row moved. Unbuilt: issue #48. Until it is built a single write returns the row's prior value, so a hand can undo it. *Why:* a batch of hundreds must answer "did that land?" and "undo it". *Pinned:* `price.rs`, `c78_a_write_returns_the_prior_value_so_a_hand_can_undo_it`.
- **C81 — The effective price is the most specific statement, the game's on a tie, and only a public tab's game side is a statement.** The levels are C70's (tab coverage); the game speaks at item level (a note) and tab level (a name, C80: the nameable tab). A note or name in a non-public tab is invisible to the index (T1, the two indexed channels): residue, shown, never a side. A prior forum post is never a side. A row that cannot be read, at a level that could decide, leaves the price unresolved, never the game's by default. *Why:* a price reaches the world only through the site's index, and a page must not contradict what the site already shows. *Pinned:* the `c81_` tests in `listing.rs`.
- **C80 — The game side's tab for a nested item is the tab a user can name and publish.** A substash reads its parent's name and `public` and reports its own name beside them; a folder child reads itself; a folder's name is never a price. *Why:* a substash has no settable name or `public` of its own, and a folder is a grouping, not a tab. *Pinned:* the `c80_` tests in `listing.rs`.
