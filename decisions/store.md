# Decisions — Store: facts, realm, characters

Part of the decision registry (`AGENTS.md`, "Cross-cutting rulings"): the rulings that bind ingest, the facts schema, items, listings and liveness, the reading of intent rows (`annotations.rs`), realm, characters (`acquisition-store/src/lib.rs`, `snapshot.rs`, `corpus.rs`, `acquisition-protocol/src/realm.rs`). Read this before touching that code; the cross-cutting decisions and the invariants are in `AGENTS.md` and are always loaded. Same rules as there: one entry per ruling, in the form `tools/bothy.py`'s docstring states; the mechanism lives in the code's doc comments under the id.

## Store: facts

- **C28 — Persistence is a shared library and files, not a process.** `acquisition-store` holds the facts in SQLite, one file per account under a per-provider directory, and the account index; the daemon writes facts, and frontends read facts and read and write intent, all through the store crate. The daemon's part is `record(endpoint, params, status, body)`, and one read: the stored listing a client's stash job is judged against at submit (C164); it serves no query and never looks inside a body. *Why:* frontend-owned stores duplicate GGG traffic when two frontends pull, and daemon-served queries make the daemon an application server. *Pinned:* `tools/arch-check.sh` (check 5: the store links no member and no HTTP client; the daemon never names the intent API).
- **C30 — A refused body is evidence, never a fact.** A 2xx body that `record` refuses as malformed rolls its ingest back whole and is kept as received in `refused`, which no basis query reads; `acq store refused [id]` reads it. *Why:* a refusal that destroys its evidence turns every malformed body into a re-fetch. *Pinned:* `acquisition-store/unit/tests/lib.rs`, `an_item_without_an_id_is_malformed_and_poisons_nothing`.
- **C55 — A character's identity is its `id`; its name is its address.** A plan action carries both: the id for identity, coverage and reasons, the name for the request, from the basis listing. A name that moved fails its child honestly or lands a different id, and the next listing reconciles. Items locate at the character id. *Why:* keying on the name breaks a policy on rename, gives a recreated name the old row's freshness, and moves every item on a rename. *Pinned:* `acquisition-cli/tests/characters_wire.rs`.
- **C108 — The store gains what search needs and nothing more: a streaming read of bodies with their ingest columns under one snapshot, and a revision.** The read is one transaction over live items at live locations and, on request, the removed with when each left; league is joined as `read_items` joins it, and a removed item's place is where it was last seen. The revision advances in the transaction that changes items, locations or membership, and nothing that prunes the file may take it back. What a body says is never derived here (C103, one deriver per fact). *Why:* a second reading of place is S131's bug (two readings of "in this league"), and a revision a write can slip past is C48's stale answer (no cached search). *Pinned:* the tests in `acquisition-store/src/corpus.rs`.
- **C124 — A tool that presents itself as a read opens the store read-only and never migrates it.** The owner-run examples (`export-items`, `redact-pricing`) and any future reader outside `acq` and the daemon open through the store's read-only door, which refuses a file at another schema version with a message in words; migration belongs to the daemon and the verbs' writing door (C193, the frontends' facts door). *Why:* "nothing written" must be true of a tool that says it, and a store an older build still reads stays readable until the owner chooses to move it; the daemon and that door migrate only from the released format (facts 8), and an older file is refused with its remedy. *Pinned:* the `c124_` tests under `acquisition-store/unit/tests/`; the two examples, `acquisition-store/examples/export-items.rs` and `acquisition-plan/examples/redact-pricing.rs`.
- **C193 — A frontend reads the facts through a type that cannot write them, and its writes of them go through one door in the verbs crate.** Migration, rebuild and prune are that door's, and none is a daemon job. The door never starts a daemon. It refuses a rebuild or a prune while a daemon is live on the world, and says to stop it first. It refuses to migrate while a daemon of another contract revision is live, and says to stop it. Unbuilt: issue #212. *Why:* a rebuild that holds the write lock can fail an ingest whose request was already sent, an older daemon keeps writing a file a newer build migrated under it, and a repair that started a daemon could send to GGG as a side effect. *Pinned:* nothing yet.

## Store: intent

- **C167 — User-scoped intent lives in one file of its own, `user.db`, inside the world (C83), written only through the store crate under revision compare-and-swap as annotations are (C35), with a revision of its own that no answer's basis carries.** Its first kind is a saved search (C194, the row keeps its source); names, tags, the shop template, currency ratios and a last-posted basis are kinds to add as each is first written. It is per world, not per account: a search names no GGG id and runs over whichever account is chosen. *Why:* the annotation file's revision is a sum over every row and sits in every answer's basis (C98), so a saved search there would reload every held corpus in `acq web` and `acq-mcp` for a write that changes no answer; and C35's file is keyed on GGG ids per account, which a search is not. The alternative, a `search` scope in the annotation file with the basis's intent component counting only the kinds that bear on answers, was declined: it teaches the basis which kinds matter, a second interpreter of intent. *Pinned:* the `c167_` tests in `acquisition-store/unit/tests/annotations.rs` (the file, the kind, the one-transaction list) and in `acquisition-verbs/tests/documents.rs` (the verbs), `acquisition-cli/tests/saved_json.rs` (the terminal).
- **C194 — A saved search keeps what was asked, and the text it runs is derived at every read.** The row holds a name, a scope and the query as given: a text in the language, or a site search as a request spells one (C113, the third spelling), the search form's fields among them as the site's query JSON. The text a row runs is made when the row is read, so an opened row carries its translation's report, and a build with other tables may read a site search differently and says so. *Why:* a row that stored the translation dropped its source, so an opened search could not say what the site's search had lost and a form could not reopen what it made. *Pinned:* the `c194_` tests in `acquisition-store/unit/tests/annotations.rs` and `acquisition-verbs/tests/documents.rs`.
- **C151 — An annotation row this build cannot read is named, never dropped, never a wall, and never repaired by a read.** `list` returns every readable row and names each unreadable one beside them: scope, key, kind, revision and the parse fault. `get` answers a structured refusal with the same facts. `delete` and `put` naming the row's revision do not parse its value, so the one compare-and-swap (C35, intent written under revision compare-and-swap) can clear or replace it; at a wrong revision they answer the refusal with the revision the row stands at. Nothing rewrites a value in place. *Why:* one damaged row hid every price and could not be cleared by the only API that may write the file. *Pinned:* the `c151_` tests in `acquisition-store/unit/tests/annotations.rs`, under `acquisition-plan/unit/tests/` and in `acquisition-cli/src/price_cmd.rs`.

## Realm and characters

- **C58 — Realm is a coordinate above league, everywhere.** A policy is `realms.<R>.leagues.<L>.{tabs, characters, max_age_seconds}`; the plan envelope carries realm beside league; the snapshot is per `(realm, league)`; facts carry a realm column; realm is an explicit param on every data kind, defaulting to pc only at the decode boundary. On the wire pc is expressed by omission, and `pc` is not a legal segment value. *Why:* PoE2 1.0 ships in December 2026 and league names collide across realms. *Pinned:* `tests/realm_wire.rs`.
- **C59 — Which realms a route accepts is declared once per route (`Family::accepts`), never as one shared list.** A policy naming `tabs` under `poe2` is a structured parse error; no code path renders a stash URL with `poe2`; an unobserved URL shape is never sent. When GGG extends PoE2 to another endpoint, the change is one row and a first-contact sample. *Why:* a shared list would send a shape nobody has observed. *Pinned:* `acquisition-protocol/src/realm.rs`, `acceptance_is_per_family_as_documented`; `acquisition-daemon/src/daemon/tests/sessions.rs`, `realm_is_a_segment_before_league_or_name_and_pc_is_silent`.
- **C61 — A listed `deleted` or `expired` character is skipped with a named reason, not fetched, and a character with no `league` is reported as uncovered, never a failure.** *Why:* the invalid-request threshold (N27, the 4xx budget) makes a 404 hunt a real cost, and `expired` does not mean the league ended. *Pinned:* `acquisition-plan/unit/tests/lib.rs`, `deleted_expired_and_league_less_characters_are_skipped_never_fetched`.
- **C63 — `acq characters` and the MCP's `characters` tool print the full id beside the name.** A name is not resolved to an id at `policy set`, so the stored policy is what the human typed. *Why:* a policy names a character by id (C55, the id is identity), and the human needs the id to write it. *Pinned:* nothing yet.

## Not doing

What someone would propose and the project declines, each until the trigger it names or for good; the backlog is the repository's GitHub issues.

- An injected clock in the store: refused. The annotation wait's seam is its knob and SQLite is its clock (`busy_timeout` runs inside SQLite); the project pins the knob's parse, the expiry verdict at zero and that two writers never clobber, in process and across processes (C35, C137). Not until the store times a wait of its own (the owner, 2026-10-31, 4-0's design).
- A migration of a world file that holds an earlier build's account facts under a reserved name (`user.db`, `daemon.db`): not until `user`, a report of a real world holding one. The opener refuses it and names the deletion; the case is a mock world's, since a real username carries its discriminator (the owner, 2026-11-07, "Recovery refusal" and "Shrink and close").
