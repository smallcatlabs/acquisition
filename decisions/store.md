# Decisions — Store: facts, realm, characters

Part of the decision registry (`CONTEXT.md`, "Decisions — the registry"): the rulings that bind ingest, the facts schema, items, listings and liveness, realm, characters (`acquisition-store/src/lib.rs`, `snapshot.rs`, `corpus.rs`, `acquisition-protocol/src/realm.rs`). Read this before touching that code; the cross-cutting decisions and the invariants are in `CONTEXT.md` and are always loaded. Same rules as there: one entry per ruling, in the form `CONTEXT.md` states; the mechanism lives in the code's doc comments under the id.

## Store: facts

- **C28 — Persistence is a shared library and files, not a process.** `acquisition-store` holds the facts in SQLite, one file per account under a per-provider directory, and the account index; the daemon writes facts, and frontends read facts and read and write intent, all through the store crate. The daemon's part is `record(endpoint, params, status, body)`; it never reads the store and never looks inside a body. *Why:* frontend-owned stores duplicate GGG traffic when two frontends pull, and daemon-served queries make the daemon an application server. *Pinned:* nothing yet.
- **C29 — Bodies are stored as received except at the item seams, and `items` is the only place to look for an item.** Every item array is lifted into `items`, one row per GGG item id, keyed by its location's full coordinate (realm, league for a stash, kind, id). A fetch of a location a listing has retired is withheld: membership is the listing's, and only a listing revives a location. *Why:* raw plus parsed duplicated every body, and raw alone made every query a body scan and gave user state no key. *Pinned:* `acquisition-store/src/lib.rs`, `a_withheld_fetch_is_marked_counted_exactly_and_still_validated`.
- **C30 — A refused body is evidence, never a fact.** A 2xx body that `record` refuses as malformed rolls its ingest back whole and is kept as received in `refused`, which no basis query reads; `acq store refused [id]` reads it. *Why:* a refusal that destroys its evidence turns every malformed body into a re-fetch. *Pinned:* nothing yet.
- **C54 — Authority is the coarser observation's.** A listing owns membership, address, league and liveness; a fetch owns contents and nothing more, and never revives what a listing retired. A location is its full coordinate; a parent tab's fetch is its substashes' listing; a listing that revives a retired row clears its `fetched_at`; membership is per response, never a timestamp match. *Why:* the same fault turned up in five places before the rule was stated once. *Pinned:* `acquisition-store/src/lib.rs`, `a_late_fetch_never_revives_a_location_a_listing_retired`, `substash_membership_follows_the_parents_fetch_and_the_parents_fate`.
- **C55 — A character's identity is its `id`; its name is its address.** A plan action carries both: the id for identity, coverage and reasons, the name for the request, from the basis listing. A name that moved fails its child honestly or lands a different id, and the next listing reconciles. Items locate at the character id. *Why:* keying on the name breaks a policy on rename, gives a recreated name the old row's freshness, and moves every item on a rename. *Pinned:* `acquisition-cli/tests/characters_wire.rs`.
- **C56 — Every item row records the array it came from (`container`, an ingest fact), and `skills` (PoE2) and `guardian` (PoE1) are lifted arrays.** An item-shaped array a character body carries under any other name is the drift tripwire: counted, shown in `store status`, never lifted, never a failure. *Why:* a guardian's items carry the character's own slot names, so the item alone cannot say which array it sits in. *Pinned:* `acquisition-store/src/lib.rs`, `container_is_an_ingest_fact_and_moving_between_arrays_is_a_change`, `an_unknown_item_array_trips_the_drift_counter_without_failing`.
- **C57 — A PoE2 item-granted skill is a property of its host, never an item fact.** The id-less gem a weapon or shield carries in `socketedItems`, repeated as `skills[0]`, with anything socketed into it, stays in the host's JSON and the envelope, counted (`_granted`), never a row and never a refusal; every other id-less item is still refused. This holds until GGG changes how granted skills are reported. *Why:* `Item.id` is documented optional and this is the case that omits it; a synthetic identity would double the entry. *Pinned:* `acquisition-store/src/lib.rs`, `an_item_granted_skill_stays_in_place_and_is_not_an_item`.
- **C108 — The store gains what search needs and nothing more: a streaming read of bodies with their ingest columns under one snapshot, and a revision.** The read is one transaction over live items at live locations and, on request, the removed with when each left; league is joined as `read_items` joins it, and a removed item's place is where it was last seen. The revision advances in the transaction that changes items, locations or membership, and nothing that prunes the file may take it back. What a body says is never derived here (C103, one deriver per fact). *Why:* a second reading of place is S131's bug (two readings of "in this league"), and a revision a write can slip past is C48's stale answer (no cached search). *Pinned:* the tests in `acquisition-store/src/corpus.rs`.

## Realm and characters

- **C58 — Realm is a coordinate above league, everywhere.** A policy is `realms.<R>.leagues.<L>.{tabs, characters, max_age_seconds}`; the plan envelope carries realm beside league; the snapshot is per `(realm, league)`; facts carry a realm column; realm is an explicit param on every data kind, defaulting to pc only at the decode boundary. On the wire pc is expressed by omission, and `pc` is not a legal segment value. *Why:* PoE2 1.0 ships in December 2026 and league names collide across realms. *Pinned:* `tests/realm_wire.rs`.
- **C59 — Which realms a route accepts is declared once per route (`Family::accepts`), never as one shared list.** A policy naming `tabs` under `poe2` is a structured parse error; no code path renders a stash URL with `poe2`; an unobserved URL shape is never sent. When GGG extends PoE2 to another endpoint, the change is one row and a first-contact sample. *Why:* a shared list would send a shape nobody has observed. *Pinned:* nothing yet.
- **C60 — The store's realm is the request's realm, stamped from the params, never from the entry's `realm` field.** The removal rule is realm-scoped, so it may under-retire when lists span realms and never over-retires. *Why:* the character list is per realm (N42, per-realm character lists), and a realm read per entry could retire another realm's rows. *Pinned:* nothing yet.
- **C61 — A listed `deleted` or `expired` character is skipped with a named reason, not fetched, and a character with no `league` is reported as uncovered, never a failure.** *Why:* the invalid-request threshold (N27, the 4xx budget) makes a 404 hunt a real cost, and `expired` does not mean the league ended. *Pinned:* `acquisition-plan/src/lib.rs`, `deleted_expired_and_league_less_characters_are_skipped_never_fetched`.
- **C62 — A character changed when a listing newer than our fetch reports a different `experience` or `league`.** This is the sibling of a tab's count arm. The planner is facet-symmetric: one `Selection` serves tabs and characters, and the store's liveness rule is consumed, not restated. *Why:* the listing's experience is the cheapest evidence of play, as a tab's count is of change. *Pinned:* `acquisition-plan/src/lib.rs`, `character_freshness_reads_experience_forward_from_a_newer_listing`.
- **C63 — `acq characters` and the MCP's `characters` tool print the full id beside the name.** A name is not resolved to an id at `policy set`, so the stored policy is what the human typed. *Why:* a policy names a character by id (C55, the id is identity), and the human needs the id to write it. *Pinned:* nothing yet.
