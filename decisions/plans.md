# Decisions — Intent, plans, apply

Part of the decision registry (`CONTEXT.md`, "Decisions — the registry"): the rulings that bind the sync policy, the planner, plan envelopes, quote, apply and its gates (`acquisition-plan`, `acquisition-store/src/annotations.rs`, the `apply` kind in `daemon.rs`). Read this before touching that code; the cross-cutting decisions and the invariants are in `CONTEXT.md` and are always loaded. Same rules as there: one entry per ruling, in the form `CONTEXT.md` states; the mechanism lives in the code's doc comments under the id.

## Intent, plans, apply

- **C36 — The sync policy is the first annotation: a per-account declaration of desired coverage and freshness, compiled by the frontend's planner into minimal requests.** It is not a scheduler. A `metadata.items` count can prove a tab changed, never that it did not. A `policy set` replaces only the realms it names, and a realm named with no leagues is dropped; `--replace` (MCP `replace`) replaces the whole; the MCP names the revision it replaces (C52, no blind replace). *Why:* the C++ tracked-set and clean-refresh semantics describe this one object. *Pinned:* `acquisition-plan/src/lib.rs` (the count heuristic, the strict parse, `a_first_merge_drops_a_realm_named_with_no_leagues`), `plan_json.rs`, `plan_loop.rs`.
- **C37 — A tab id in the sync policy covers that tab and its children.** A map or unique tab's substashes are planned once their stubs are on record, the cycle after the parent's first fetch; a folder's children at once; a stub counting 0 is skipped with a named reason. *Why:* the intent behind naming a map tab is its contents, and an exact id match left its substashes uncovered. *Pinned:* `acquisition-plan/src/lib.rs`, `a_named_map_tab_covers_its_substashes_the_cycle_after_its_first_fetch`.
- **C39 — The planner lives in `acquisition-plan`, which depends on the protocol and the store and is linked by frontends only.** It owns policy compilation and plan construction; the store exposes neutral snapshots, never half a planner. *Why:* the dependency graph, not discipline, keeps the daemon from linking the planner. *Pinned:* `tools/docs-check.sh` (the edge is refused), `snapshot.rs`.
- **C40 — `quote` is its own protocol request, never a flag on `Submit`: a read-only, non-reserving projection over the daemon's current knowledge.** It names its observation time and basis, estimates per policy and scope, and the prerequisites it cannot see; an apply may receive a different schedule. *Why:* a quote that reserved or submitted would turn an estimate into a commitment. *Pinned:* `daemon.rs`, `quote_projects_per_scope_reserves_nothing_and_names_what_it_cannot_see`; `acquisition-plan/src/lib.rs`, `with_quote`.
- **C41 — Reads observe, assertions plan, apply spends.** Store reads never start network traffic; stale facts stay readable with their freshness; only a freshness condition the caller asserts fails, with the exact `RefreshPlan` it would take. Refresh, await, read is a workflow, never a fused read. *Why:* a read that sends is traffic nobody reviewed. *Pinned:* `tools/docs-check.sh` (the store links no HTTP), `acquisition-mcp/tests/plan_loop.rs` (offline paths raise no daemon).
- **C42 — The request budget is logical work, enforced at admission: the daemon refuses a plan before any child is submitted if its logical bound exceeds `max_requests`.** A budget over actual wire sends is a different feature. The tripwire and the lifetime ceiling stand apart from it. *Why:* a plan's bound is known before any send, a wire count only after. *Pinned:* `daemon.rs`, `apply_admission_refuses_bad_vocabulary_and_blown_budgets_whole`; `acquisition-cli/tests/apply_loop.rs`.
- **C43 — Apply is its own pure fan-out parent job kind, `apply`, never the `refresh` parent.** Its params carry the plan's actions as explicit `(kind, params)` child tuples; the parent sends nothing itself and submits exactly one child per tuple. The daemon admits vocabulary, not meaning: single-request kinds only, checked at submit before a job id exists. *Why:* the refresh parent re-lists by construction, which contradicts executing exactly the listed actions, and the daemon stays plan-blind. *Pinned:* `daemon.rs`, `apply_fans_out_exactly_its_tuples_and_records_through_the_store`; `acquisition-cli/tests/apply_loop.rs`.
- **C44 — Apply refuses a plan whose sync-policy revision is no longer the stored one.** A plan is authorization derived from intent at a revision, and an edit since revokes it; the check is frontend-side against a fresh read just before submit. Fact drift does not refuse: the authorization is the bounded action set, and a target's own later fetch spends its action (C111, each request spent once). *Why:* the compare-and-swap that guards writing intent guards spending it, and replanning is free. *Pinned:* `acquisition-cli/tests/plan_json.rs`; fact drift: `acquisition-plan/src/lib.rs`, the `c44_` tests.
- **C76 — One door: an explicit selection (`--tabs`, `--all`, `--characters`) compiles to a plan through the same envelope and apply, and the ad hoc `refresh` kind retires when nothing submits it.** A selection plan's precondition set is empty, since it derives from no stored intent; its listing, freshness and two-cycle semantics are ruled when it is built. Unbuilt: issue #21. *Why:* two doors to one task is one door too many. *Pinned:* nothing yet.
- **C77 — Freshness is judged at compile time against the window; a later replan that refetches facts which aged past the window during a long cycle is correct, not a fault.** A plan does not pre-fetch what is fresh at compile. *Why:* an offline plan has no honest cycle estimate, and a cycle-based handle ("fresh as of every run") is the C++ model the policy replaced (C36, the sync policy). *Pinned:* nothing yet.
- **C111 — A plan spends each request once.** An action is spent when its target was fetched at or after the plan's snapshot, or when the daemon already holds the same request for the account. Apply sends the unspent actions and names the spent ones; it never refuses, so a replayed plan sends nothing. The check is frontend-side before submit, as C44's (the revision check); two applies racing both send. A fetch of what is fresh is asked for by name, never by replay. *Why:* binding authorizes a fetch, not a fetch per application. *Pinned:* `acquisition-cli/tests/seat_faults.rs`, `acquisition-mcp/tests/plan_loop.rs`.

## Not doing

What someone would propose and the project declines, each until the trigger it names or for good; the backlog is the repository's GitHub issues.

- Dynamic `--deep` fan-out: not until live evidence that two-cycle reconciliation hurts.
- Type-level sync-policy filters: not until a policy author needs an exclusion the parent-covers-children rule cannot express.
- A daemon-side check against two applies of one plan racing: not until a duplicate fetch is traced to concurrent applies in a journal; until then both send.
