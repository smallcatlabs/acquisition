# Decisions — Intent, plans, apply

Part of the decision registry (`AGENTS.md`, "Cross-cutting rulings"): the rulings that bind the sync policy, the planner, plan envelopes, quote, apply and its gates (`acquisition-plan`, `acquisition-store/src/annotations.rs`, the `apply` kind in `kinds.rs`). Read this before touching that code; the cross-cutting decisions and the invariants are in `AGENTS.md` and are always loaded. Same rules as there: one entry per ruling, in the form `tools/bothy.py`'s docstring states; the mechanism lives in the code's doc comments under the id.

## Intent, plans, apply

- **C39 — The planner lives in `acquisition-plan`, which depends on the protocol and the store and is linked by frontends only.** It owns policy compilation and plan construction; the store exposes neutral snapshots, never half a planner. *Why:* the dependency graph, not discipline, keeps the daemon from linking the planner. *Pinned:* `tools/arch-check.sh` (the edge is refused), `snapshot.rs`.
- **C40 — `quote` is its own protocol request, never a flag on `Submit`: a read-only, non-reserving projection over the daemon's current knowledge.** It names its observation time and basis, estimates per policy and scope, and the prerequisites it cannot see; an apply may receive a different schedule. *Why:* a quote that reserved or submitted would turn an estimate into a commitment. *Pinned:* `acquisition-daemon/src/daemon/tests/quote.rs`, `quote_projects_per_scope_reserves_nothing_and_names_what_it_cannot_see`; `acquisition-plan/src/lib.rs`, `with_quote`.
- **C41 — Reads observe, assertions plan, apply spends.** Store reads never start network traffic; stale facts stay readable with their freshness; only a freshness condition the caller asserts fails, with the exact `RefreshPlan` it would take. Refresh, await, read is a workflow, never a fused read. *Why:* a read that sends is traffic nobody reviewed. *Pinned:* `tools/arch-check.sh` (the store links no HTTP), `acquisition-mcp/tests/plan_loop.rs` (offline paths raise no daemon).
- **C42 — The request budget is logical work, enforced at admission: the daemon refuses a plan before any child is submitted if its logical bound exceeds `max_requests`.** A budget over actual wire sends is a different feature. The tripwire and the lifetime ceiling stand apart from it. *Why:* a plan's bound is known before any send, a wire count only after. *Pinned:* the apply rows of `c127_admission_through_the_door` in `acquisition-daemon/src/daemon/tests/queue.rs` (the rows named "apply of" and "an apply's budget"); `acquisition-cli/tests/apply_loop.rs`.
- **C43 — Apply is its own pure fan-out parent job kind, `apply`, never the `refresh` parent.** Its params carry the plan's actions as explicit `(kind, params)` child tuples; the parent sends nothing itself and submits exactly one child per tuple. The daemon admits vocabulary, not meaning: single-request kinds only, checked at submit before a job id exists. *Why:* the refresh parent re-lists by construction, which contradicts executing exactly the listed actions, and the daemon stays plan-blind. *Pinned:* `acquisition-daemon/src/daemon/tests/parents.rs`, `apply_fans_out_exactly_its_tuples_and_records_through_the_store`; `acquisition-cli/tests/apply_loop.rs`.
- **C44 — Apply refuses a plan whose sync-policy revision is no longer the stored one; a plan compiled from an explicit selection carries no policy revision and the apply checks none.** A policy plan is authorization derived from intent at a revision, and an edit since revokes it; a selection plan's authorization is the selection itself. The check is frontend-side against a fresh read just before submit. Fact drift does not refuse: the authorization is the bounded action set, and a target's own later fetch spends its action (C111, each request spent once). *Why:* the compare-and-swap that guards writing intent guards spending it, and replanning is free. *Pinned:* `acquisition-cli/tests/plan_json.rs`; fact drift and the selection plan: `acquisition-plan/unit/tests/lib.rs`, the `c44_` tests.
- **C111 — A plan spends each request once.** An action is spent when its target's fetch landed after the plan's snapshot, told by the response it landed in rather than the clock, or when the daemon already holds the same request for the account. Apply sends the unspent actions and names the spent ones; it never refuses, so a replayed plan sends nothing. The check is frontend-side before submit, as C44's (the revision check); two applies racing both send. A fetch of what is fresh is asked for by name, never by replay. *Why:* binding authorizes a fetch, not a fetch per application. *Pinned:* `acquisition-cli/tests/seat_faults.rs`, `acquisition-mcp/tests/plan_loop.rs`; by response: `acquisition-plan/unit/tests/lib.rs`, `c111_a_selection_sends_what_was_fetched_in_its_own_second_and_once`.

## Not doing

What someone would propose and the project declines, each until the trigger it names or for good; the backlog is the repository's GitHub issues.

- Dynamic `--deep` fan-out: not until live evidence that two-cycle reconciliation hurts.
- Type-level sync-policy filters: not until a policy author needs an exclusion the parent-covers-children rule cannot express.
- A daemon-side check against two applies of one plan racing: not until a duplicate fetch is traced to concurrent applies in a journal; until then both send.
- `notes` on a selection plan (a selection-shaped `plan_notes`, the league a fetched list lacks, as a policy plan notes it): not until a consumer asks for it.

Rulings retired to the comment under their id at each file that holds them; the first file named carries the reason, and an id here is never reused (`tools/bothy.py`, the retired rule).

- **C36 — The sync policy is the first annotation: a per-account declaration of desired coverage and freshness, compiled by the frontend's planner into minimal requests.** *Held by:* `crates/acquisition-plan/unit/tests/lib.rs`, `crates/acquisition-cli/tests/plan_json.rs`, `crates/acquisition-mcp/tests/plan_loop.rs`.
- **C126 — A policy may name a league the account's fetched league list does not hold; the policy receipt and the plan say so, and nothing refuses.** *Held by:* `crates/acquisition-cli/tests/new_league.rs`, `crates/acquisition-store/unit/tests/lib.rs`, `crates/acquisition-mcp/tests/journey.rs`.
- **C37 — A tab id in the sync policy covers that tab and its children.** *Held by:* `crates/acquisition-plan/unit/tests/lib.rs`.
- **C76 — One door: an explicit selection (`--tabs`, `--all`, `--characters`, a page's ticks) compiles to a plan through the same envelope and apply, and the ad hoc `refresh` kind is gone.** *Held by:* `crates/acquisition-plan/unit/tests/lib.rs`, `crates/acquisition-cli/tests/web.rs`, `crates/acquisition-cli/tests/apply_loop.rs`.
- **C77 — Freshness is judged at compile time against the window; a later replan that refetches facts which aged past the window during a long cycle is correct, not a fault.** *Held by:* `crates/acquisition-plan/unit/tests/lib.rs`.
