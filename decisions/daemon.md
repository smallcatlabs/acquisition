# Decisions — Daemon, jobs, protocol, accounts

Part of the decision registry (`AGENTS.md`, "Cross-cutting rulings"): the rulings that bind the daemon, the job model, the protocol, the client, sessions and accounts (`acquisition-daemon/src/daemon.rs` and the files under `daemon/`, `acquisition-client/src/client.rs`, `locator.rs`, `artifact.rs`, `acquisition-protocol/src/protocol.rs`, `job.rs`, `acquisition-store/src/jobs.rs`, `index.rs`). Read this before touching that code; the cross-cutting decisions and the invariants are in `AGENTS.md` and are always loaded. Same rules as there: one entry per ruling, in the form `tools/bothy.py`'s docstring states; the mechanism lives in the code's doc comments under the id.

## Daemon, jobs, protocol

- **C3 — The daemon spawns lazily and exits when idle.** A use verb spawns a daemon when none runs; an observation verb never spawns or replaces (C10, single-version handshake); a frontend spawns only where its own policy allows (C13, the MCP never in real mode). The daemon exits after an hour (`ACQ_IDLE_SHUTDOWN`) with no connections and no queued work; a live job holds it however long the limiter makes it wait. Unbuilt: issue #80. A job verb with no login still spawns, and its refusal says that a daemon started and when it will exit. `daemon stop` and `daemon status` exist for debugging. *Why:* no stray processes and no start-up ceremony. *Pinned:* `acquisition-daemon/src/daemon/tests/idle.rs`, `idle_verdict_*`.
- **C5 — The job queue is a priority queue from the start, though one level is in use.** *Why:* a reorder is a field write, not a data-structure migration. *Pinned:* nothing yet.
- **C6 — The job queue persists: a `jobs` table in a per-daemon `daemon.db`, written at every state change and read back at start.** Memory stays the runtime source of truth and the table its mirror. Ids never run ahead of disk; a daemon that cannot open the table refuses to start; a failed queue write is sticky. One daemon per store directory holds the world lock (C83, a world's exclusive lock). *Why:* the queue was the one thing a restart lost once results moved to the store. *Pinned:* `acquisition-daemon/src/daemon/tests/queue.rs`, `a_broken_queue_is_fatal_to_restore`; `persisted_queue.rs`.
- **C7 — A job's `params` travel on `JobInfo` as submitted, and they are public.** Every connected client sees them, so params never carry a secret; tokens are obtained inside the daemon, never passed in. *Why:* a job a person cannot identify cannot be managed, and rendering it is the client's business. *Pinned:* nothing yet.
- **C127 — A client submits only the kinds the daemon's kind table lists for clients, in the provider modes each row names, and every param that shapes a send is judged at submit.** Before an id exists the door refuses an unknown kind, the daemon's own `probe`, a mock-only kind in real mode, a path param missing where required, too long, or not one segment as any server reads it, a `sleep` beyond its bound, and params over theirs; no refusal quotes a client value whole. A path param renders as one encoded segment; a row the door would refuse fails in its words. *Why:* a client's string that reaches a URL or a timer unjudged can steer a send off the route its limiter key names, or panic a job already persisted. *Pinned:* `acquisition-daemon/src/daemon/tests/queue.rs`, the `c127_` tests.
- **C8 — The protocol has a subscribe channel from the start: job-state events over the same socket.** *Why:* GUI push updates and `jobs --watch` come nearly free, and adding a channel later is painful. *Pinned:* `acquisition-cli/tests/watch_recovery.rs`.
- **C9 — The protocol is JSON lines over a Unix socket or a named pipe.** *Why:* boring, debuggable and cross-platform. *Pinned:* `acquisition-protocol/tests/wire.rs`.
- **C85 — A connection carries one request in flight, and a subscription has a connection of its own: hello, subscribe, subscribed, then events only.** Events are invalidation hints, never a complete stream: a subscriber snapshots after subscribing and re-reads before relying on its view, and after `resync_required` or any disconnect it subscribes and snapshots again. A frame has a bound, and an oversize or malformed frame is answered with an error, not a closed socket. `hello` and `daemon_stop` are a stable plane every version parses. *Why:* a client must see its losses to recover from them. *Pinned:* the `c85_` tests in `acquisition-protocol/tests/wire.rs` and `acquisition-client/tests/contract.rs`.
- **C10 — The handshake is single-version: a mismatched daemon is replaced, never negotiated with.** A client uses a daemon only when its provider and runtime identity (C84, contract and artifact) match what it would itself spawn; the identity changes with the code it governs and never derives from Git or a hand-kept value. A use verb may replace a mismatch; an observation verb never spawns or replaces, and reports absence and mismatch distinctly; an autonomous client (the MCP) never replaces. *Why:* a compatibility matrix is a reconciliation swamp, and an observer that replaced a daemon once cost a live run. *Pinned:* `acquisition-cli/tests/daemon_observe.rs`.
- **C84 — The runtime identity (C10, single-version handshake) is two values: the shared-contract revision, a digest of the protocol and store sources, manifests and lock, and the daemon artifact, the executable the daemon hashes at startup and a client compares with the sibling `acqd` it would spawn.** A mismatch on either is reported by name; a rebuilt `acqd` under a live daemon is an artifact mismatch; a daemon-only change moves only the artifact. *Why:* the contract answers "can I use it" and the artifact "is it the one I would start", and each sees a failure the other cannot. *Pinned:* the `c84_` tests in `daemon_observe.rs`.
- **C83 — A world is a canonical, provider-neutral store root; its daemon holds an exclusive lock on it for its lifetime, and in real mode a per-OS-user lock no root bypasses.** A use path creates the root, then canonicalises and locks it; observation creates nothing. `hello` names the root, and a client refuses a daemon on another world; the endpoint is C112's (derived and private). Durable state (`daemon.db`, the rails state) lives in the world; the log and journal are bounded diagnostics elsewhere. *Why:* the persisted queue and the one-daemon bound were held by documentation, and the tripwire's state lived where the OS clears it at reboot. *Pinned:* `acquisition-cli/tests/world.rs`, the `c83_` tests.
- **C112 — The daemon's endpoint is derived from the world and the OS user, never chosen by hand.** Only that user can serve or reach it, and a client speaks to it only after verifying the server runs as that user. *Why:* a socket name is discovery, not ownership, and on Windows a named pipe's namespace is machine-wide, so privacy is the endpoint's property, not a directory's. *Pinned:* `acquisition-cli/tests/world.rs`.
- **C132 — The real-mode lock's path derives from the OS user alone, in the user's own data directory.** The home comes from the password database (on Windows, the profile directory from the process token), never from a variable; the lock sits in a private `run` directory beside the default store; the socket stays in the runtime directory (C112, the derived endpoint). Another user or mount namespace stays external concurrency (C31, one daemon, many sessions); a home that cannot hold the lock means no real-mode daemon, refused by name. *Why:* every temp directory is moved by a variable or age-cleaned under a held lock, and two locks are two gates. *Pinned:* `acquisition-store/src/world.rs`, `c83_the_lock_path_reads_no_environment`; `acquisition-cli/tests/world.rs`, the `c83_c31_` test.
- **C86 — The handshake has a deadline: a peer that accepts and does not answer `hello` within 5 s is unresponsive, its own verdict on every door, never absence.** Nothing spawns or replaces over it, and the report names the world lock's recorded holder for the hand that stops it. *Why:* a healthy daemon answers `hello` in milliseconds whatever the limiter holds, so a late `hello` is a wedged daemon, and an unbounded read hung every door on it. *Pinned:* the `c86_` tests in `acquisition-client/tests/contract.rs`.
- **C147 — A door and a ledger read take the world they act on; the environment is read once, at the frontend's construction.** `Client::connect`, `Client::observe`, `Persisted::observe` and `World::observe` take the world, and the environment-reading form calls them, kept for the binaries' doors; a `Frontend` passes its captured world to every call, so a frontend over a chosen world is expressible and nothing asserts two readings agree. A client keeps the child it spawns and reaps it, reports a failed stop on the replace path, and gives a child that exited on the world lock one more look for the winner (C86, the handshake deadline) before the spawn is called failed. *Why:* a long-lived frontend holds more than one world and outlives the daemons it spawns. *Pinned:* the `c147_` tests.
- **C137 — A deadline's contract is its behaviour at expiry, not the number: a test pins it by forcing expiry. No test asserts a wall-clock bound a slow machine can miss.** A liveness deadline widens through a named knob (`ACQ_HELLO_WITHIN`, `ACQ_STARTUP_WITHIN`, `ACQ_ANNOTATION_WAIT`, the idle exit's), set by the isolation list so a starved runner cannot fail a healthy path; the knob at zero forces the expiry. A new lifecycle that waits across processes is designed as a state machine over an injected clock. *Why:* the Windows gate failed most first runs on deadlines measured against a starved runner, and each repriced budget only promoted the next margin. *Pinned:* the `c137_` tests in `acquisition-client/tests/contract.rs` and `acquisition-store/src/annotations.rs`.
- **C82 — At most one installation targets a world.** The installation places one `acqd` beside every frontend, and a frontend spawns only the sibling of its own canonical executable: no `PATH`, no configured path, no embedded mode; no sibling, no spawn, reported. Tests and drivers locate it the same way. A second installation targeting one world is a design event. *Why:* C10's "the runtime it would itself spawn" (the handshake's identity) must name one file, or two installations thrash. *Pinned:* `acquisition-client/src/locator.rs`, the `c82_` test; `tools/release-smoke.sh`.
- **C23 — Work that needs many requests is a parent job that submits child jobs.** A parent finishes when its last descendant does, gives up its dispatcher task and scheduling key while it waits, and cancels its descendants when cancelled; its failure carries its children's tally (done, failed, cancelled, the failed ids) as a field, never as prose a client reads back. *Why:* the queue, dispatcher, priorities, ETAs and events already work per job, so children get them free. *Pinned:* `acquisition-daemon/src/daemon/tests/parents.rs`, `cancelled_children_do_not_make_a_parent_successful`, `a_cancelled_parent_cannot_gain_children`; `acquisition-protocol/tests/wire.rs` (the failure sample); `acquisition-cli/tests/apply_loop.rs`.
- **C27 — A client that disappears leaves its jobs running.** Ctrl-C, a closed terminal or a crash cancels nothing. The daemon runs in a process group of its own on every OS. A client reattaches by job id (`acq result <id>`), answered across daemon restarts. *Why:* the sends are committed either way. *Pinned:* `acquisition-client/tests/contract.rs`; `acquisition-cli/tests/provider_default.rs`, `a_lazily_started_daemon_survives_a_ctrl_c_at_the_prompt_that_started_it`.
- **C133 — The daemon has one exit, and every cause reaches it.** `daemon stop`, the idle verdict and a terminating signal run one path: submits are refused as stopping; a job parked before its send returns to waiting (C25); the jobs past admission, the token refreshes and a pending login have 15 s of wall-clock time to land and be recorded; then the logs are checkpointed, the socket removed and the process exits. At the bound the drain ends; a second signal, or an exit not gone 3 s past the bound, ends the process at once, leaving what it cuts running on disk for C6 to replay. A pending login holds the idle verdict. *Why:* `stop` or a replace by a newer frontend could cut a refresh in flight and lose its rotated token and journal line. *Pinned:* `exit.rs`.
- **C134 — A broken internal invariant ends the process; a listener failure never does.** A panic is logged through a handle that takes no lock, a marker names the job it ran in, and the process aborts; the next lifetime fails that job as faulted instead of replaying it (C6), and a probe's marker also closes its route for the cooldown, failing the jobs that would recreate it, so a body that breaks the daemon is sent once. An error from `accept` is logged, with a backoff, and served through; an unreachable daemon idles out (C3). *Why:* a caught task panic left a stray that never idled out, and one accept error dropped the world lock with sends in flight. *Pinned:* `exit.rs`, `a_fault_marker_fails_its_job_once`, `a_listener_error_is_served_through`, `a_faulted_probe_closes_its_route`.
- **C45 — With no daemon to ask, an observer reads the queue from the ledger on disk: what waits, what was recorded running, when it was last written; never "no outstanding work".** `acq jobs`, `status` and `result`, `daemon status` and the MCP's `list_jobs`, `job_status`, `job_result` and `daemon_status` answer `running: false` with the persisted queue beside it, read through the store's read-only `Persisted` view and never while a daemon answers. *Why:* a halted daemon idles out with its queue on disk (C25, a halt leaves jobs waiting), and an observer never spawns (C10, single-version handshake). *Pinned:* the `c45_` tests in `persisted_queue.rs`, the CLI's and the MCP's; `acquisition-verbs/tests/`.
- **C123 — The stand-in provider serves real-shaped items from a committed fixture.** Its bodies are the owner's own items, exported from his store under his grant and chosen for the traits the journey needs, or hand-written to the census (`search/DIGEST.md`) where his store holds none; compiled into `acqd`, never a path read at run time; never a body from the trade site or another player. *Why:* a user, a seat and the journey test meet search and price through fetching, on bodies whose shape is the API's today, and the fixture's provenance stays the owner's and the project's. *Pinned:* `acquisition-daemon/src/mockggg.rs`, `every_fixture_item_`; `acquisition-cli/tests/goldens/journey/a_first_session.txt` and its twin `acquisition-mcp/tests/journey.rs`.

The owner's grant covers items from any of his stores, so a trait the fixture lacks is taken from one of them before it is hand-written.

## Accounts and sessions

- **C31 — Multi-account is one daemon holding many sessions, not a daemon per account.** The Cloudflare bound is per IP and held as per-process state, so two daemons on one machine make a burst neither sees; the world lock (C83, one daemon per world) holds it among one OS user's real-mode daemons, and other users and processes stay external concurrency. Limiter and probe state is keyed per `(account, policy)` for `Account` rules. *Why:* GGG counts `Account` rules per account. *Pinned:* `acquisition-daemon/src/ratelimit/tests/spec.rs`, `account_rules_are_paced_per_account`.
- **C49 — Only the session layer interprets accounts.** Everywhere else an account is data: a field on the job, a path segment for the store, an opaque key component for the limiter. *Why:* an `if account == …` outside the session layer is a second interpreter of what an account means. *Pinned:* nothing yet.
- **C50 — The stable account key is the profile `uuid`, fetched at login and required.** A login whose profile fetch fails fails whole: no provisional identity, no minted keys, no rename repair. The fetch belongs to its login's lifetime: a later lifetime fails it at restore and sends nothing for it, and the user logs in again. `accounts.json` maps username, discriminator and provider to the uuid; fact files are named by username (refetchable), annotation files by uuid. *Why:* intent references identity, and an unstable key is what the C++ app's legacy buyouts paid for. *Pinned:* `acquisition-daemon/src/daemon/tests/login.rs`, `a_login_whose_profile_fetch_fails_fails_whole`; `queue.rs`, `c50_a_lost_logins_profile_fetch_fails_at_restore_and_sends_nothing`.
- **C51 — The daemon keeps no default account; selection is stateless.** Every submit carries `account`; omitted, it resolves only when exactly one session exists, and otherwise the daemon refuses with the list. The CLI resolves `--account` and `ACQ_ACCOUNT` against `accounts.json` client-side, so reads never spawn a daemon; matching is exact, never by prefix. A job has exactly one account; cross-account work is a frontend loop. *Why:* a default held in the daemon is state every client would have to guess. *Pinned:* `acquisition-client/tests/contract.rs`.
- **C135 — The access token is kept in the keyring beside the refresh token and restored with it; a lifetime refreshes only at expiry.** Unbuilt: issue #55. *Why:* one token POST per lifetime was one per minute of idle cycling. *Pinned:* nothing yet.
- **C136 — The submitter `daemon` is the daemon's own: a client submit that names it is refused at the door.** Under the owner's delegation. *Why:* a rule keyed on the daemon's own work, as C50's lost login is, must rest on a mark no client can forge. *Pinned:* `acquisition-daemon/src/daemon/tests/queue.rs`, `c136_a_client_submit_as_the_daemon_is_refused_and_sends_nothing`.
- **C144 — The daemon reports no success it did not earn.** A store that cannot be opened or written after a send fails the job, and the failure carries the fetched body as an optional payload so the send is not wasted; every credential-store result reaches the caller and the words the user reads, so logout and forget say what the keyring did, and a rename or a failed save clears the entry it leaves behind; a staged login token serves the login's own profile job alone (C136, the daemon's own submitter); the account index is written atomically, synced, under the one lock. *Why:* a success the user is told and the tree does not hold costs a session or a secret, and it is the fault every review keeps finding in prose. *Pinned:* the `c144_` tests in the daemon, store, protocol, CLI.
- **C148 — No credential-store or account-index I/O runs under the daemon's shared lock, and `hello` is answered under no lock such I/O can hold.** A refresh, a login, a logout and a forget change the session table under `shared` and do their keyring and index I/O under one credentials lock, on a blocking thread, publishing the result under `shared` after; a waiter on a refresh and a bearer read under a permit are served at the install, never the save; a login being recorded refuses a second; the exit's drain waits for a save in flight to its bound. Unbuilt: issue #81. *Why:* a keychain prompt under `shared` made every client report the daemon unresponsive and held jobs behind their token read (#81). *Pinned:* nothing yet.

## Not doing

What someone would propose and the project declines, each until the trigger it names or for good; the backlog is the repository's GitHub issues.

- Priority levels beyond one: not until a second level is in use (C5 keeps the field).
- Packaging beyond the GitHub archives (an installer, Windows signing, notarization, another channel): not until the owner reopens a channel, or a user is stopped by Gatekeeper on a browser-fetched macOS archive or by SmartScreen on a Windows one.
- A second installation targeting one world: refused under C82; a consumer that needs one is a design event.
- keyring 4's per-platform stores in place of keyring 3's backends: not until a sandboxed package or a provisioning-profile bundle.
- A GUI-hosted daemon: refused; the GUI spawns `acqd` as the CLI does, and phase 4 records the spawn policy.
- musl static Linux builds below the glibc 2.35 floor: not until a user on an older distribution.
