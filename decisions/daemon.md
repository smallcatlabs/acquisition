# Decisions — Daemon, jobs, protocol, accounts

Part of the decision registry (`CONTEXT.md`, "Decisions — the registry"): the rulings that bind the daemon, the job model, the protocol, the client, sessions and accounts (`acquisition-daemon/src/daemon.rs`, `acquisition-client/src/client.rs`, `locator.rs`, `artifact.rs`, `acquisition-protocol/src/protocol.rs`, `job.rs`, `acquisition-store/src/jobs.rs`, `index.rs`). Read this before touching that code; the cross-cutting decisions and the invariants are in `CONTEXT.md` and are always loaded. Same rules as there: one entry per ruling, in the form `CONTEXT.md` states; the mechanism lives in the code's doc comments under the id.

## Daemon, jobs, protocol

- **C3 — The daemon spawns lazily and exits when idle.** A use verb spawns a daemon when none runs; an observation verb never spawns or replaces (C10, single-version handshake); a frontend spawns only where its own policy allows (C13, the MCP never in real mode). The daemon exits after a short period with no connections and no queued work. A job verb with no login still spawns, and its refusal says that a daemon started and when it will exit. `daemon stop` and `daemon status` exist for debugging. *Why:* no stray processes and no start-up ceremony. *Pinned:* `daemon.rs`, `idle_verdict_*`.
- **C5 — The job queue is a priority queue from the start, though one level is in use.** *Why:* a reorder is a field write, not a data-structure migration. *Pinned:* nothing yet.
- **C6 — The job queue persists: a `jobs` table in a per-daemon `daemon.db`, written at every state change and read back at start.** Memory stays the runtime source of truth and the table its mirror. Ids never run ahead of disk; a daemon that cannot open the table refuses to start; a failed queue write is sticky. One daemon per store directory holds the world lock (C83, a world's exclusive lock). *Why:* the queue was the one thing a restart lost once results moved to the store. *Pinned:* `daemon.rs`, `a_broken_queue_is_fatal_to_restore`; `persisted_queue.rs`.
- **C7 — A job's `params` travel on `JobInfo` as submitted, and they are public.** Every connected client sees them, so params never carry a secret; tokens are obtained inside the daemon, never passed in. *Why:* a job a person cannot identify cannot be managed, and rendering it is the client's business. *Pinned:* nothing yet.
- **C8 — The protocol has a subscribe channel from the start: job-state events over the same socket.** *Why:* GUI push updates and `jobs --watch` come nearly free, and adding a channel later is painful. *Pinned:* `acquisition-cli/tests/watch_recovery.rs`.
- **C9 — The protocol is JSON lines over a Unix socket or a named pipe.** *Why:* boring, debuggable and cross-platform. *Pinned:* `acquisition-protocol/tests/wire.rs`.
- **C85 — A connection carries one request in flight, and a subscription has a connection of its own: hello, subscribe, subscribed, then events only.** Events are invalidation hints, never a complete stream: a subscriber snapshots after subscribing and re-reads before relying on its view, and after `resync_required` or any disconnect it subscribes and snapshots again. A frame has a bound, and an oversize or malformed frame is answered with an error, not a closed socket. `hello` and `daemon_stop` are a stable plane every version parses. *Why:* a client must see its losses to recover from them. *Pinned:* the `c85_` tests in `acquisition-protocol/tests/wire.rs` and `acquisition-client/tests/contract.rs`.
- **C10 — The handshake is single-version: a mismatched daemon is replaced, never negotiated with.** A client uses a daemon only when its provider and runtime identity (C84, contract and artifact) match what it would itself spawn; the identity changes with the code it governs and never derives from Git or a hand-kept value. A use verb may replace a mismatch; an observation verb never spawns or replaces, and reports absence and mismatch distinctly; an autonomous client (the MCP) never replaces. *Why:* a compatibility matrix is a reconciliation swamp, and an observer that replaced a daemon once cost a live run. *Pinned:* `acquisition-cli/tests/daemon_observe.rs`.
- **C84 — The runtime identity (C10, single-version handshake) is two values: the shared-contract revision, a digest of the protocol and store sources, manifests and lock, and the daemon artifact, the executable the daemon hashes at startup and a client compares with the sibling `acqd` it would spawn.** A mismatch on either is reported by name; a rebuilt `acqd` under a live daemon is an artifact mismatch; a daemon-only change moves only the artifact. *Why:* the contract answers "can I use it" and the artifact "is it the one I would start", and each sees a failure the other cannot. *Pinned:* the `c84_` tests in `daemon_observe.rs`.
- **C83 — A world is a canonical, provider-neutral store root; its daemon holds an exclusive lock on it for its lifetime, and in real mode a per-OS-user lock no root bypasses.** A use path creates the root, then canonicalises and locks it; observation creates nothing. `hello` names the root, and a client refuses a daemon on another world; the endpoint is C112's (derived and private). Durable state (`daemon.db`, the rails state) lives in the world; the log and journal are bounded diagnostics elsewhere. *Why:* the persisted queue and the one-daemon bound were held by documentation, and the tripwire's state lived where the OS clears it at reboot. *Pinned:* `acquisition-cli/tests/world.rs`, the `c83_` tests.
- **C112 — The daemon's endpoint is derived from the world and the OS user, never chosen by hand.** Only that user can serve or reach it, and a client speaks to it only after verifying the server runs as that user. *Why:* a socket name is discovery, not ownership, and on Windows a named pipe's namespace is machine-wide, so privacy is the endpoint's property, not a directory's. *Pinned:* `acquisition-cli/tests/world.rs`.
- **C86 — The handshake has a deadline: a peer that accepts and does not answer `hello` within 5 s is unresponsive, its own verdict on every door, never absence.** Nothing spawns or replaces over it, and the report names the world lock's recorded holder for the hand that stops it. *Why:* a healthy daemon answers `hello` in milliseconds whatever the limiter holds, so a late `hello` is a wedged daemon, and an unbounded read hung every door on it. *Pinned:* the `c86_` tests in `acquisition-client/tests/contract.rs`.
- **C82 — At most one installation targets a world.** The installation places one `acqd` beside every frontend, and a frontend spawns only the sibling of its own canonical executable: no `PATH`, no configured path, no embedded mode; no sibling, no spawn, reported. Tests and drivers locate it the same way. A second installation targeting one world is a design event. *Why:* C10's "the runtime it would itself spawn" (the handshake's identity) must name one file, or two installations thrash. *Pinned:* `acquisition-client/src/locator.rs`, the `c82_` test; `tools/release-smoke.sh`.
- **C23 — Work that needs many requests is a parent job that submits child jobs.** A parent finishes when its last descendant does, gives up its dispatcher task and scheduling key while it waits, and cancels its descendants when cancelled. *Why:* the queue, dispatcher, priorities, ETAs and events already work per job, so children get them free. *Pinned:* `daemon.rs`, `cancelled_children_do_not_make_a_parent_successful`, `a_cancelled_parent_cannot_gain_children`.
- **C27 — A client that disappears leaves its jobs running.** Ctrl-C, a closed terminal or a crash cancels nothing. A client reattaches by job id (`acq result <id>`), answered across daemon restarts. *Why:* the sends are committed either way. *Pinned:* `acquisition-client/tests/contract.rs`.
- **C45 — With no daemon to ask, an observer reads the queue from the ledger on disk: what waits, what was recorded running, when it was last written; never "no outstanding work".** `acq jobs`, `daemon status` and the MCP's `list_jobs` and `daemon_status` answer `running: false` with the persisted queue beside it, read through the store's read-only `Persisted` view and never while a daemon answers. *Why:* a halted daemon idles out with its queue on disk (C25, a halt leaves jobs waiting), and an observer never spawns (C10, single-version handshake). *Pinned:* the `c45_` tests in `persisted_queue.rs`, the CLI's and the MCP's.

## Accounts and sessions

- **C31 — Multi-account is one daemon holding many sessions, not a daemon per account.** The Cloudflare bound is per IP and held as per-process state, so two daemons on one machine make a burst neither sees; the world lock (C83, one daemon per world) holds it among one OS user's real-mode daemons, and other users and processes stay external concurrency. Limiter and probe state is keyed per `(account, policy)` for `Account` rules. *Why:* GGG counts `Account` rules per account. *Pinned:* `ratelimit.rs`, `account_rules_are_paced_per_account`.
- **C49 — Only the session layer interprets accounts.** Everywhere else an account is data: a field on the job, a path segment for the store, an opaque key component for the limiter. *Why:* an `if account == …` outside the session layer is a second interpreter of what an account means. *Pinned:* nothing yet.
- **C50 — The stable account key is the profile `uuid`, fetched at login and required.** A login whose profile fetch fails fails whole: no provisional identity, no minted keys, no rename repair. `accounts.json` maps username, discriminator and provider to the uuid; fact files are named by username (refetchable), annotation files by uuid. *Why:* intent references identity, and an unstable key is what the C++ app's legacy buyouts paid for. *Pinned:* `daemon.rs`, `a_login_whose_profile_fetch_fails_fails_whole`.
- **C51 — The daemon keeps no default account; selection is stateless.** Every submit carries `account`; omitted, it resolves only when exactly one session exists, and otherwise the daemon refuses with the list. The CLI resolves `--account` and `ACQ_ACCOUNT` against `accounts.json` client-side, so reads never spawn a daemon; matching is exact, never by prefix. A job has exactly one account; cross-account work is a frontend loop. *Why:* a default held in the daemon is state every client would have to guess. *Pinned:* `acquisition-client/tests/contract.rs`.
