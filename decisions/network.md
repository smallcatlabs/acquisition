# Decisions — Network and rate limiting

Part of the decision registry (`AGENTS.md`, "Cross-cutting rulings"): the rulings that bind the limiter, the gate, probes, rails, OAuth traffic, anything that sends (`acquisition-daemon/src/ratelimit.rs`, `gate.rs`, `rails.rs`, `auth.rs`, the choke point). Read this before touching that code; the cross-cutting decisions and the invariants are in `AGENTS.md` and are always loaded. Same rules as there: one entry per ruling, in the form `tools/bothy.py`'s docstring states; the mechanism lives in the code's doc comments under the id.

## Network and rate limiting

- **C17 — The rate limiter is a custom policy layer that parses GGG's headers, over a simple enforcement mechanism.** *Why:* GGG's header-driven limits are too specific for an off-the-shelf policy. *Pinned:* the `acquisition-daemon/src/ratelimit/tests/spec.rs` tables.
- **C18 — Limiter state is keyed by policy name, per account for `Account`-scoped rules, and learned only from headers.** There is no local token counting: a wait comes from the last `X-Rate-Limit-*` state and the responses' arrival times, padded by the server's timing bucket, and rules are classified by position (Q4, initial versus sustained). *Why:* same-name policies share counters across endpoints (N6, shared policy counters), so endpoint-keyed state would be a migration later. *Pinned:* the `acquisition-daemon/src/ratelimit/tests/spec.rs` tables.
- **C19 — A counted send whose response carries no usable policy headers is paced as if the server counted it, as a send lost in transport is.** The job still fails and is never retried. *Why:* a run of headerless origin 503s (N35, the origin's bare 503) went out unpaced, and this bounds an outage at the policy's own rate with no new policy. *Pinned:* `acquisition-daemon/src/ratelimit/tests/spec.rs`, `headerless_counted_response_paces_as_if_counted`; `daemon.rs`, `headerless_503_fails_its_job_and_paces_the_next_send`.
- **C20 — Endpoint discovery is a visible `probe` job: one HEAD per endpoint per daemon lifetime, queued by the daemon before the first real send.** *Why:* HEAD probing is GGG's sanctioned pattern (N16, HEAD probes sanctioned), and it is visible because everything that touches GGG is a job and HEAD has regressed server-side before (N20, HEAD carries the headers). *Pinned:* `acquisition-daemon/src/ratelimit/tests/spec.rs`, `probes_teach_without_counting_and_degrade_on_n20_shapes`.
- **C21 — The global burst bound sits at the daemon's HTTP send boundary and spans each request from just before dispatch until its body completes.** OAuth code exchange and refresh are inside it; the browser's authorize is outside; the dispatcher has no global cap on job tasks. *Why:* Cloudflare watches bursts across policies and fronts the token endpoint (N33, the token endpoint's policy), so capacity must describe sends, not waiting work. *Pinned:* `acquisition-daemon/src/ratelimit/tests/spec.rs`, `common_gate_caps_gets_until_response_bodies_complete`; `gate.rs`, `permit_lifetime_enforces_global_cap_and_per_policy_serialization`.
- **C22 — The frozen C++ network design (`acquisition-qt:docs/design/network-redesign.md`) is a property source, not an architecture template.** The Rust code keeps the properties that design numbers D3, D4, D5 and D8, with three adaptations: OAuth token traffic inside the common gate (N33, the token endpoint's policy); plain FIFO among the eligible policies; no 250 ms spacing between sends. Changing an adaptation is a design change. *Why:* the properties protect the GGG relationship, and the mechanisms were shaped by Qt. *Pinned:* nothing yet.
- **C24 — A `refresh_token` grant the provider rejects with a 4xx other than 429 is dead: no refresh is sent until `acq auth` or logout.** The mark persists across restarts, with or without the tripwire. *Why:* a dead grant re-sent per flight is pointless traffic on a Cloudflare-fronted endpoint. *Pinned:* `daemon.rs`, `rejected_refresh_grant_disables_further_refreshes_until_logout`, `a_completed_login_clears_the_dead_grant_mark`.
- **C87 — An access token the provider rejects with a 401 is dead.** No send leaves the gate carrying it once the rejection has landed, and the account's next send is the refresh. The choke point reads the token after admission and reports a 401 before the rejecting send's permit drops; a waiter whose token is gone refreshes outside the permit and retries once; sends already on the wire may land 401 too; the job that met the 401 fails and says so. *Why:* a rejected bearer re-sent per job is a timed stream of 401s spending the invalid-request budget (N34, the dead bearer re-sent; N27, the 4xx budget). *Pinned:* `daemon.rs`, `rejected_access_token_*`.
- **C25 — A rails halt leaves queued network jobs waiting; nothing fails for want of a send.** A halted daemon with only waiting jobs idles out, and its successor holds the queue until `reset-tripwire`. The ceiling is per lifetime and not persisted. *Why:* a halt that failed its never-sent jobs made the rerun refetch everything. *Pinned:* `daemon.rs`, `a_halted_daemon_with_only_waiting_jobs_is_idle`, `halted_daemon_refuses_refresh_before_any_send`.
- **C26 — A 429 re-queues its job, keeping its place, behind the limiter's hold; after `MAX_429_RETRIES` (2) it fails with the evidence.** A 403 or a 503 is never retried. *Why:* violations are structural, so recovery is required; frequent ones revoke the app (N10, violations revoke access), so it is bounded; invariant 3 (no retry through Cloudflare) covers the Cloudflare shapes. *Pinned:* `daemon.rs`, `dispatcher_never_retries_403_or_503`, `dispatcher_exhausts_on_third_429_without_a_fourth_send_or_final_sleep`.
- **C32 — Per-route knowledge that headers cannot teach lives in one place, `Daemon::declare_route_knowledge`, and strict observation is the default everywhere else.** Only `/profile` (policyless: N38) and `/account/leagues` (no probe, its HEAD counts: N39) are declared, and the list is not generalised. *Why:* "any headerless 2xx is fine" reopens the blind spot strict observation closed. *Pinned:* `acquisition-daemon/src/ratelimit/tests/spec.rs`, `a_declared_policyless_route_accepts_a_headerless_2xx_and_nothing_else_does`; `daemon.rs`, `declared_route_knowledge_holds_against_the_mock`.
- **C33 — The rate limiter's spec is test tables, not prose.** `docs/design/network-ground-truth.md` is the input; "given these headers, wait N seconds" tests are the permanent, enforced spec. *Why:* a table the gate runs cannot drift from the code as prose does. *Pinned:* the `acquisition-daemon/src/ratelimit/tests/spec.rs` tables.
- **C88 — The real provider is the default; the mock is opted into.** `ACQ_PROVIDER=mock` selects the in-process mock; unset or `ggg` is the real API; any other value, or `ACQ_GGG` at all, is refused at start. A human starts a real-mode daemon: the CLI spawns or replaces one in real mode only with a terminal on stderr; a mock spawn is free; `acq-mcp` never spawns in real mode (C13, the MCP's spawn policy). The rails and one daemon per provider stand. *Why:* one gate protects the relationship, not callers kept away (C14, agents through one gate), and a mock default put every offline read behind a flag. *Pinned:* the `c88_` tests in `provider_default.rs`, the CLI's and the MCP's.
