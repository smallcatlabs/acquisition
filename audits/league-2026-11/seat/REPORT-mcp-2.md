## 1. Before touching anything

**What the brief told me (the brief).** The tool is Acquisition's MCP server `acq-mcp`; the store holds `GERWARIC#7694` (a copy of the person's real collection, ~50 MB, with their prices, no session) and `seat` (logged in at the terminal, no keyring, a daemon running for four hours after its last connection). Calls go to a mock of GGG's API. None of that is counted below as the README's or the tool's.

**What the README told me (README alone, before any call).**
- *Can do:* download stash tabs and characters into a local store; search them offline (incl. translating trade-site search URLs); price items by hand (`price_set/clear`, with undo); render forum shop pages to paste (it never posts); keep a league fresh by a *sync policy* -> *plan* -> *apply* loop; run jobs through a daemon. 25 MCP tools, listed by group ("Your agent").
- *Needs:* store, search, pricing and shop need no daemon and no network. Fetching (jobs, `apply_plan`, `submit_job`, `cancel_job`) needs a daemon; against GGG `acq-mcp` never starts one, a person starts it with `acq auth check` (keyring) or `acq auth` (no keyring). A login is a person's act at a terminal. Without a keyring a login lives only as long as the daemon.
- *Before an agent can use it:* the person unpacks the binaries together, logs in (`acq auth`, or `ACQ_PROVIDER=mock acq auth` for the stand-in), and puts the server in `.mcp.json` / Claude Desktop config with `command` = path to `acq-mcp`, plus `env` `ACQ_PROVIDER: mock` for the stand-in and `ACQ_STORE_DIR` matching `acq`'s.
- *New league:* `acq leagues` names it; write the first policy with `if_revision: 0` (lands only where none is stored); adding a league to an existing policy means writing the realm back with every league it keeps (naming only the new league drops Standard); then plan/apply with `--league <name>` until the plan says nothing to do; the first plan is the listings (tab list, character list if stale), later plans fetch every tab; read each plan's work and ceiling first.
- *Rate limit:* tabs ~30 per 5 minutes seen so far; holds up to 5 minutes; a first sync of a few hundred tabs takes most of an hour.
- *I would not call without asking:* `apply_plan`/`submit_job` against the real API on a big plan (time and rate budget), `set_sync_policy` with `replace: true` or over an existing policy, `price_set`/`price_clear` on the person's real prices, `cancel_job` on jobs I did not start. In this world the brief makes all of these safe.
- The README points at `CLI-REFERENCE.md`, `AGENTS.md`, source files in the Knobs table, `SECURITY.md`, `CONTRIBUTING.md`, `decisions/<area>.md` — pointers I cannot follow here. None was needed for T0.

**What `open` (call 1) told me that the README had not.**
- The server is running with `provider: mock` (instructions' first line) — the README does not say the server announces its provider.
- `list_jobs`, `job_status`, `job_result`, `daemon_status` answer *without* a daemon, from a ledger on disk; `refresh_plan` adds a running daemon's quote without starting one.

**What the README said that `open` did not.** The daemon's idle exit (an hour, `ACQ_IDLE_SHUTDOWN`), what to type when none runs (`acq auth` / `acq auth check`), the rate-limit clock (30 tabs / 5 min), the new-league procedure as a sequence, and that a policy naming only the new league drops Standard (the `set_sync_policy` text says a named realm is replaced whole, which implies it).

## 3. Faults

Worst first.

1. **A search's age is the whole scope's, not the answer's** (calls 32, 33, 36, 37). Every answer reports `scope.oldest_fetch_age`/`newest_fetch_age`, which look like "how old these facts are", but they are identical for 187 matches and for 22,623 items and change only with the realm. A count view (calls 33, 37) has no age of the matched items at all. Should: report the oldest/newest fetch of the *matches* (or label the scope figures as the scope's). Both a person and an agent would quote the wrong age.
2. **`submit_job` takes a tab id the store has never listed and spends a request on it** (calls 59–61). Warranted failure (my id was wrong), but the record says only "404 Not Found" — no `kind`, no `offers`, no "this id is not in the stored listing (8 tabs listed, call 20)". Should: warn or refuse at submit when the id is unknown to the store, or at least say so in the failure. Against GGG it costs a rate-limited request. An agent hits it more than a person (a person picks tabs from a list).
3. **Wrong-account refusal is `kind: "not_logged_in"`** (call 58). Warranted, and enough to recover (offers are right) — but the `kind` misclassifies a typo as a login problem; a program branching on `kind` would ask the person to log in. Should: `unknown_account` or similar. Agent-only (a person reads the text).
4. **No undo removes a price after a replacement** (calls 47, 49, 54). The replacement's undo (call 49) restores 2 divine; the first receipt's clear (call 47) is stale. The refusal (call 54) was warranted and its offer recovered it, so this is a two-call path with a refusal in it. Should: a receipt could carry "back to the start" as well as "back one step". Both would hit it.
5. **`shop_render`'s freshness says nothing without a sync policy** (call 52 `freshness.policy: "not_set"`) while every position on the page is 50 days old (call 39 `stash_listing_fetched_at_age: "50d ago"`). Should: say the positions' age regardless. A person pasting the page would hit it.
6. **"Begin with search and no arguments" refuses on this store** (calls 1, 24). Warranted given two realms, and the offers are exactly right (call 25), so recovery is one call — but the instruction's first step always errs on a multi-realm store. Agent-only.
7. **`never_fetched_by_type` holds fetched counts** (call 25): `{"type":"MapStash","tabs":2582,"fetched":93,"items":803}` under a name that says never-fetched; `"type":"character"` inside a list of tab types. Misleading to both.
8. **`unknown_name` refusal has no offers** (call 26): it lists every key, which is enough, but unlike every other refusal sends no ready request. Minor, agent-only.
