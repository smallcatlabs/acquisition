## 1. Before touching anything

First account, from what `open` printed (call 1) and nothing else.

What it can do: search the person's stored items with a query language (`describe` prints it); `show` one item whole; a trade-site search (URL, id or JSON) is translated offline to a query text and run over the store (call 1, instructions and `search` text). Store readers: search, show, accounts, tabs, characters, store_status, item_events, sync_policy. These need no daemon and no network (call 1).

What needs what: refreshing data (submit_job, apply_plan, job_status, job_result, cancel_job, list_jobs, daemon_status) needs the local daemon, and through it the game's API; login is done by the human with the `acq` CLI (call 1). refresh_plan and set_sync_policy are local and offline; apply_plan spends the plan on the daemon.

What I would not run without asking: apply_plan and submit_job (they send requests to the game's API and consume rate limit), set_sync_policy (it writes the person's stored intent), cancel_job. The instructions say a price is only the owner's own listing, and that a trade search run here is over the store, not the site's public listings (call 1) — so "would the site show the same" must be answered from the translation's fidelity, not assumed.

Plan for looking at the world: search with no arguments, store_status, accounts, tabs, characters; read-only.

## 3. Faults
Worst first. "Person" = a person at a terminal would hit it too; "agent" = only an agent would.

1. A single search answer is far larger than the answer needs and is not shortenable. A ring search with 20 rows was 30696 bytes (call 8); 22 rows 30821 bytes (call 23); even 3 rows 12565 bytes (call 9) and a counts-only view 13987–15893 bytes (calls 10, 11), because each answer repeats the whole trade clause table and every term's `failed/lacked/matched` block with its own request. My harness stored the two largest and showed 2 KB (calls 8, 23), so I lost the answer and paid a second call (call 9), or chose from a first row (call 23). A person would see it scroll; an agent would also pay in context. Agent mostly.
2. `tabs` for Standard answered 745672 bytes (call 6); the door printed the first 3000 characters. It has no limit or filter argument, so a whole league's tab list cannot be read; I could not see the tab ages. The door's cut is the door's rule, but the tool has no way to ask for less. Person and agent both.
3. A counts table cuts at 20 buckets by default and says so with `left_out` and `left_out_needs: "--limit"` (call 11: 36 left out), an unexplained flag name for an MCP caller; the argument is `view.counts.limit`, which I guessed from the schema's `limit` (call 17, 19 accepted it). Agent.
4. Place answers do not say how old the data is per row. The row carries only a place; the age (`first_seen`/`last_seen`) shows only in `show` (calls 14, 24), and the search's `scope.oldest_fetch/newest_fetch` spans 3.2 million seconds (call 3). For "where do I pick it up" this is the number that matters. Person and agent.
5. The same search language gives different totals than its own term tables suggest: each term counts over every league in scope (call 16: 168 for the rarity term, 160 total), which reads like a contradiction. It is stated in the `search` text ("each term alone over every item in scope") but it is easy to misread. Agent mostly.
6. `fidelity: "ambiguous"` is given for armour, rarity, scourge and map clauses (calls 12, 15, 16, 18, 21), with the reason in each clause's notes, but never says in which direction (more or fewer than the site). For T4 and T6 the direction mattered and I could only say "may". Person and agent.
7. `kind` and `tier` as count keys were refused with a one-line reading list (calls 5, 20); `map_tier` was named, `kind` got no suggestion that fit ("int", "line", "links"). Refusal told me enough for `tier`, not for `kind` (call 5; I dropped it and used `league`, which worked, call 7). Agent.

## 4. What the instructions and the tool texts did not say
- A bare `search` needs a realm when the store holds two; the instructions say "over a store of several realms that is refused", but not that this store is such: call 2 refused, call 3 worked with the offered request. I expected it in `instructions`, which did say it in general.
- That a count table is cut at 20 and the knob is `view.counts.limit`: I expected it in the `search` text, learned it at call 11 (`left_out_needs`).
- That a `trade` query plus `view` is accepted for counts (call 10), that a `text` beside it must be the exact translation (stated in `search`; call 11 I dropped `trade` as told).
- That equipped and inventory items on characters appear as a tab-less bucket (`-has:tab`, calls 10, 11, 17, 19). Expected in `search` text or `describe`, learned at call 10.
- That "(Remove-only)" is in tab names as the person wrote them; the tool does not explain it (calls 6, 10).
- That the result size of a search cannot be limited below about 3.7 KB of text (call 22 was the smallest search, 3724 bytes of text), and that the harness may store large answers rather than show them (calls 8, 23). I expected the `search` text to warn of the answer size.
- That `show` takes `body: true` and returns the stored JSON as an escaped string (call 24): read in the tool's schema, not in the instructions.

## 5. The tool's own words
Right: "a refusal is a result marked isError with readings and offers to go on from" (call 1, then call 2: the offers were exactly what I needed, and the pc request was valid as printed). "A price is the owner's own listing" (call 1) is right and useful: no item I looked at had a price (calls 14, 24). Misleading or missing: the `instructions` string is one long paragraph that mixes the store tools, the plan/apply tools and the daemon; the first useful sentence for an agent (what to begin with) is buried in the middle. `describe`'s text says the whole is over 100 KB and tells me to name sections; I did not call `describe` at all, since the trade translation was enough. I read and never used: `refresh_plan`, `apply_plan`, `submit_job`, `sync_policy`, `item_events`, `daemon_status`, `list_jobs`, `characters`, `accounts` (no call to any of them; the brief's world has no daemon). Words I did not understand: "C96", "C14", "C84" and "(C45)" appear in refusals and tool texts as code references with no meaning given (call 1, call 2); "facts_version", "folders" and "list_seen" in `scope` (call 3) are not defined where they appear; "securable" in the status note (call 9).

## 6. What you would ask of the tool
- A way to ask a search for less: a `view` with no clause table and no per-term blocks, or a `brief` flag (calls 8, 23, 9).
- A `limit` and a tab-id filter on `tabs` (call 6).
- A row's `last_seen` or tab `fetched_at` in each search row, so the age of a place is seen with the place (calls 3, 24).
- A direction on every "ambiguous" clause: "the site may show more/fewer" (calls 12, 16, 21).
- A counts key for category or class, listed in the `search` text, and a suggestion that fits when a key is unknown (calls 5, 20).
- A note on what "Remove-only" means for a tab, or a per-tab flag that says it (calls 6, 10).
