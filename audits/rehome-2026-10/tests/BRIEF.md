# Brief: the test read

One of the three reads of the rehome step
(`brainstorming-notes/36-the-road-to-the-agent-release.md`, "Step 1",
"Beside it"). The question, from the note, asked once per test: **what
change to the product makes this fail, and is that change a boundary?**
(`TESTING-NOTES.md`: "what else here reads as a check but cannot
fail".)

The suite is 780 test functions. Four runners take one group each; your
prompt names yours. Your fixed input is
`data/inventory-<group>.tsv` beside this brief (`path  line  name
kind`, generated by `inventory.py`): one row per test function, and you
answer for every row.

## Rules that bind you

- Read-only outside `audits/rehome-2026-10/tests/`, and inside it write
  only the files this brief names for your group. Never edit, create or
  delete any other file — above all, never touch a test or the code it
  tests. Never commit, push, fetch, stash, checkout or spawn agents.
- **Never run `cargo`, `acq`, `acqd`, `acq-mcp` or anything under
  `tools/`.** The quality gate is running in this tree; a second cargo
  corrupts its run. This is a read: every answer comes from the source.
  Read-only git is allowed (`git log`, `git show`, `git grep`).
- No network.
- Read `TESTING-NOTES.md` whole first (the send journal is the contract
  surface; tests pin boundaries, never mechanisms), then `CONTEXT.md`,
  "Working style", then the decision file for your group's area
  (`decisions/`), so that you know what the boundaries are: the daemon
  protocol and the send journal, the store crate's read and write API,
  the plan and price documents, the query language and the answer's
  JSON, the CLI's and the MCP's output. A decision id in a test's name
  or comment (`C<n>`) names the boundary it claims to hold.
- A large file is read by section (`grep -n`, then `sed -n` by range),
  never whole and never skipped. Read each test's body and enough of
  its helpers to answer; a helper that does the asserting is where the
  answer is.

## The answer per test

One row in `data/read-<group>.tsv`, tab-separated, header:

`path  line  name  fails_when  class  confidence  note  verdict`

- `path`, `line`, `name`: copied from the inventory row.
- `fails_when`: the smallest change to the *product* that turns this
  test red, in one clause of at most 160 characters ("the limiter
  sending before the window's reset", "the answer's `basis` losing its
  build name"). Not a description of what the test does.
- `class`, one of:
  - `boundary` — the change is one a user, a frontend, GGG or a
    recorded decision would notice.
  - `mechanism` — the test reaches into internals and would fail on a
    refactor that changes no observable behaviour (a private struct's
    field, the order of internal calls, an exact internal message).
  - `cannot-fail` — no change to the product turns it red: it asserts
    on its own fixture, compares a value with itself, has no assertion
    on the path it claims, is vacuous when a collection is empty, or
    swallows the failure. Say which in `note`, with the line.
  - `weak` — it can fail, but a wrong product that a reader of the
    test's name would expect it to catch passes it. Say the wrong
    product in `note`.
  - `duplicate` — another test in your group fails on exactly the same
    changes and no others. Name it in `note`.
  - `harness` — it tests the test harness, a generator or a fixture
    loader, never the product. Not a fault; classed apart.
- `confidence`: high, medium or low. Low is an honest answer where a
  test's reach could not be traced; say what stopped you in `note`.
- `note`: required for every class but `boundary` and `harness`, one
  clause, citing `path:line`.
- `verdict`: leave empty; it is the owner's.

No tabs or newlines inside a cell. Do not class a test `mechanism`
merely because it is a unit test inside `src/`: a unit test that holds
a decision's property at the lowest rung that can hold it is
`boundary`.

## The speed lever, named separately

Note 36: "the generated-search binaries at smaller case counts locally
and full in CI is a knob, not a redesign." For every property or
generated test in your group (`kind` is `proptest`, or the test loops
over generated cases), add a row to `data/cases-<group>.tsv`:

`path  line  name  cases  where_set  knob`

— the number of cases, the `path:line` that sets it, and whether an
environment variable or a config already changes it (`none` if not).
Do not time anything.

## Outputs, for your group

- `data/read-<group>.tsv` and `data/cases-<group>.tsv` as above.
- `README-<group>.md`, written last from the two files: a headline
  block of at most six lines (the count per class; the count of rows at
  low confidence), then one line per row classed `cannot-fail`, `weak`
  or `duplicate`, then at most ten `mechanism` rows you judge the most
  disposable. Guide: under 8 KB.

## Acceptance

`data/read-<group>.tsv` has exactly one row per inventory row, in the
inventory's order, and every `cannot-fail`, `weak` and `duplicate` row
names the line that shows it.

## Report back (at most 300 words)

Counts per class; the rows you are least sure of; what you left out and
why; the one cut you would most want reversed.
