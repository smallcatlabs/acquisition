## `acq`

```text
Acquisition CLI: the real GGG API by default; ACQ_PROVIDER=mock talks to the in-process mock

Usage: acq [OPTIONS] <COMMAND>

Commands:
  auth          Log in via OAuth (real GGG, or the mock under ACQ_PROVIDER=mock). The login completes only once its own profile job lands the account uuid; the mock's page accepts any username, so a second account is one login apart
  profile       The account profile (account:profile)
  characters    List characters on the logged-in account. A route's first use queues a visible `probe` job — one HEAD that learns the policy and the account's current counters before anything real is sent
  character     Fetch one character with its equipment and inventory
  leagues       List the account's leagues: one a line, with its realm and category (`--json`: GGG's answer whole). A new league is listed here the day it opens
  accounts      Accounts this machine has logged into (the store's index; no daemon)
  tabs          Tabs of a league, from the shared store (no daemon round-trip): the counts first, then every tab with its type, items, age and id. A league of more than thirty tabs is counted by type with its ten largest tabs instead; --expand lists every one. --type and --never-fetched select the tabs listed — the never fetched of one type by name, which a refresh takes — under the league's counts. `--json` is the same document: the counts, `by_type`, and `rows`, the tabs listed, with `left_out` counting the rest
  search        Search the items the store holds (no daemon): a query over every live item of one realm, answered with the canonical query, the scope searched, the total, and the rows with the lines the query touched — then each term's counts over the scope, matched, failed, lacked, undecided, and the basis. Every count has a route: the command that returns exactly its members, printed where a next step hangs on it and every one under `--routes`. `--json` is the answer whole, in the same order, the query as text and as tree, a count's request where its route is printed; a failure is `{"error", "kind", "readings"}`, with `offers` where a way on is a request `--request` reads. `--describe` prints the language, and what this build refuses by name
  show          One item as the search derives it, live or removed (no daemon): its fields, its place, every line with its kind, template and numbers, and what could not be read; `--json` the same, structured. `--body` adds the body as the store holds it, which is still there when deriving could not read it
  store         The shared store itself (what the daemon writes; every frontend reads)
  stashes       List stash tabs for a league: a second rate-limit policy, paced in parallel with the character routes
  stash         Fetch one stash tab (or one substash of a map/unique tab)
  refresh       Refresh tabs: one stash-list request, then one `stash` child job per selected tab. Selection is explicit — there is no default. (The ad-hoc `--tabs`/`--all` kind and the plan path are two doors to one task; the ad-hoc kind retires once nothing submits it.) Keeping a league up to date is the plan path: `acq policy set` once, then `--plan` and `--apply` until the plan says nothing to do — a map or unique tab's substashes are known only once the tab is fetched, so a first sync takes two rounds, and each apply ends by saying what is left
  policy        The per-account sync policy: the declared coverage and freshness that `acq refresh --plan` compiles into requests
  submit        Submit any job kind by hand
  demo          Submit a burst of fetch jobs against the mock's 5-per-10 s policy and watch the rate limiter queue them (the ETAs are the limiter's prediction, corrected by headers)
  dash          Live dashboard (TUI): rate limiter state (enter expands a policy: bucket state, the observed X-Rate-Limit headers, per-endpoint sends), job queue, HTTP sends, recent errors, a rails halt in red. With --json, prints one snapshot and exits
  version       What this build is: the package version, the shared-contract revision the daemon handshake compares — a digest over the protocol and store crates' manifests and `src` trees, the root manifest and the lock, never a git commit — and the sibling `acqd` a job command would start, as found on disk (path, length, modification time; no hash — the run record hashes it). This reports the candidate; `acq daemon status` reports the daemon running. `--json`: {"version", "contract", "provider", "acqd": {path, len, mtime_ns} | null}, plus "acqd_absent" (why) when acqd is null; `--version` is the human form of the first two
  jobs          The live jobs: id, parent, kind, target (from params), state (`↻n` counts 429 re-queues), priority, account, submitter, ETA. Every waiting and running job is listed, and the ten most recent finished ones; the last line counts them all, and says when the next waiting job starts and when the last one does. `--json` is every job the daemon holds. Observes only: with no daemon running it never spawns one, and answers from the ledger on disk instead — the non-terminal rows as the last daemon left them, without ETAs, and how long ago they were written; `--json`: `running: false`, `persisted` (`jobs`, `written_at`; `null` when this shell's world has no queue yet). A job command spawns a successor that restores them; `cancel` then acts on them
  status        One job's state and ETA. A large ETA is the limiter holding, not a hang: holds can reach 300 s plus the timing bucket. With no daemon running, the job as the ledger on disk records it (never spawns)
  result        A finished job's payload or error. Kept on disk (7 days done, 30 failed, by default) and answered whether or not a daemon runs; a job still waiting or running is an error unless --wait. A failed or cancelled job exits 1. A failed fetch's refused body is in `acq store refused <id>`, not here
  cancel        Cancel a waiting or running job; cascades to every descendant still waiting. Needs the running daemon and never starts one
  set-priority  Change a waiting job's priority; higher runs sooner and the queue reorders live. Needs the running daemon and never starts one
  price         The listing state (no daemon): what every item, tab and character is priced as — by hand, in game, and how the two stand
  reference     Reference data the binary ships (no store, no daemon): the currency table, by version
  shop          The forum shop (no daemon, sends nothing): render the page set a hand price would post, every omission counted with its reason
  daemon        Inspect, stop or reset the daemon. A job command or `acq auth` starts one on demand; `stop` is for a login not in the keyring, which ends with the daemon, and for the README's longer-lived daemon recipe, which starts a new one while none runs
  help          Print this message or the help of the given subcommand(s)

Options:
      --json               Emit structured JSON instead of human-readable output: one document on stdout, a failure included (`{"error", "kind"}`). A job verb's is `{"outcome", "payload", "job_id", "account"}`, and a failed job's carries `error` in place of `payload`; without the flag it prints the payload alone
      --account <ACCOUNT>  Which account to act as: a username (with or without `#…`) or uuid. Defaults to `ACQ_ACCOUNT`. With neither, a verb that reads the store takes the sole account known on disk (`acq accounts`) and a job verb the sole account logged in (`acq auth status`); with more than one, the verb refuses and lists them. A job's progress line and its JSON name the account it ran as [env: ACQ_ACCOUNT=]
  -h, --help               Print help
  -V, --version            Print version
```

## `acq search`

```text
Search the items the store holds (no daemon): a query over every live item of one realm, answered with the canonical query, the scope searched, the total, and the rows with the lines the query touched — then each term's counts over the scope, matched, failed, lacked, undecided, and the basis. Every count has a route: the command that returns exactly its members, printed where a next step hangs on it and every one under `--routes`. `--json` is the answer whole, in the same order, the query as text and as tree, a count's request where its route is printed; a failure is `{"error", "kind", "readings"}`, with `offers` where a way on is a request `--request` reads. `--describe` prints the language, and what this build refuses by name

Usage: acq search [OPTIONS] [QUERY]

Arguments:
  [QUERY]  The query: `class:helmets rarity=rare`, `line("# to maximum Life").arg1>=70`, `pseudo.total_res>=80`; `acq search --describe fields` is the place to start, and bare `--describe` the whole index. None: every item in scope. One that starts with `-`, the language's not, goes after `--`, as every route prints it: `acq search --realm pc -- '-is:corrupted'`

Options:
      --realm <REALM>                  The realm searched: pc, xbox, sony, poe2, or all. Over a store holding one realm it may be omitted and the answer prints it; over several it is required, one of them or `all`
      --membership <live|all|removed>  Which items are searched: `live`, the default; `all`, which adds the removed — each row marked with when it left, at the place it was last seen; or `removed`, the removed alone. The scope block counts the live and the removed apart under either
      --query-file <FILE|->            Read the query from a file, or from stdin with `-`: a query with an apostrophe needs no shell quoting this way
      --trade <URL|ID>                 A trade site search in place of a query, translated with no network to the query a person would type: its URL (`https://www.pathofexile.com/trade/search/<league>/<id>`, or `…/search/xbox/<league>/<id>` and `sony` for a console), its id alone, or its query JSON. A URL's realm is the search's scope, so `--realm` beside one is an error; an id or JSON names no realm and takes `--realm` as a query does. The answer opens with how faithful the translation is and every clause it could not run; the clauses, each with its status, are its JSON's `query.trade`, and `--describe trade` is what becomes of each. The site's sort is reported, never applied. PoE1 only
      --trade-file <FILE|->            `--trade`, read from a file or from stdin with `-`: the query JSON as the site posts it, `{"query": …, "sort": …}` or the query object alone, needs no shell quoting this way
      --sort <VALUE>                   Order the rows by a value: `ilvl`, `stack`, `'line("T").arg1'`, `'sum("T")'`, `pseudo.total_res`. A line's scalar is its largest satisfying occurrence; an item with none sorts last either way. A sum spans every source the line has — implicit and crafted with explicit — as the row's `sorts by` shows; one source's is its form, `'sum(line("T" source=explicit).arg1)'`, the filter's own
      --desc                           Largest first
      --limit <LIMIT>                  How many rows to return — or, of a count, how many values a table lists; the rest are counted. Twenty where none is given
      --routes                         Print every count's route — the command that returns exactly its members — instead of the few a next step hangs on; under `--json`, every count's request. Beside `--next` or `--request`, the answer it runs carries them all
      --describe [<NAME,…>]            The language as this build knows it. Bare, the index: fields, what a line has, operators, closed value sets, slots, how terms compose, what a count takes, what is not built and the limits stated, with each computed value and category by name and one line (about 47 KB). Named, those entries whole with their definitions (`--describe league,line,pseudo.total_res`; a block's name is one: `--describe computed`, and `--describe trade` what `--trade` makes of each clause of a site search). `--describe all` is every entry whole, over 150 KB. `--json` is whole unless entries are named
      --count <KEY,…>                  Count the matches by a key, one table for each key named, and show no rows: a field (`tab`, `league`, `rarity`, `base`, …; `--describe counts` lists them), or `line`, the vocabulary — the templates the matching items carry, ranked, each with the term that selects it and the range of its numbers. `line:` takes the rest of the list as texts to narrow by, a table each, and `~` before one makes it a pattern: `--count tab,line:resist,life`. An item with no value is counted under `none`, one whose value could not be read under `undecided`; every count has its route (`--routes`). Given again, the flag starts a list of its own, so a field can follow a narrowed vocabulary: `--count line:resist,life --count rarity`. `realm` is not a key: `--realm` scopes the search, and a count's league names its realm
      --cross <KEY,KEY>                Count the matches by two fields at once, one table of the cells that hold an item: `--cross league,tab`
      --sum <VALUE>                    Beside each count, the sum of one number over its items: `stack`, `ilvl`, `'sum("T")'`, `pseudo.total_res`. An item lacking the thing adds nothing and is counted as lacking; one unread leaves a subtotal marked incomplete
      --fields <NAME,…>                Not built, waiting for a consumer that asks: the caller names a row's fields
      --next <TOKEN>                   Continue an answer past its limit: the token its `more` line printed, whole. The token names the query, the view, the order and the basis it continues, so no word of scope, query or view stands beside it but `--limit`; across a changed basis — a refresh, a price written — it is refused, both named, and the way on is the search from its start
      --explain <PATH>                 Explain one node of the query, named by its path — a term's as the terms block prints it (`3`), a group of terms', or a condition's inside `line( … )` or `linked( … )` (`3.1`): the root's matched and undecided counts as given, with that node forced true, and with it forced false, each beside its transformed query, the node replaced by `true()` or `false()` and nothing else changed. Counts and no rows: an error beside `--count`, `--cross`, `--sum` or `--sort`. A path the query lacks lists the query's nodes with their paths
      --context <WHICH>                What the answer is of: `matches`, the query's, as every answer is; or `corpus`, the empty query over the same scope under rows or a count, with the query typed printed as set aside and counted nowhere; beside `--explain`, which is of the query typed, an error
      --print-request                  Print the request as JSON, its account and realm resolved, and do not run it: what `--request` reads
      --request <FILE|->               Run a request read from a file, or from stdin with `-`: what `--print-request` printed, a `next` or an offer of an answer's `--json`, or a count's route — which reports both counts where its count has moved since, and wherever the basis has where the answer's `basis` is sent beside it as `counted_at`. A request is whole: no word of scope, query or view stands beside it
      --rebind                         Not built, waiting for a consumer that asks: run another account's request deliberately
  -h, --help                           Print help
```

## `acq refresh`

```text
Refresh tabs: one stash-list request, then one `stash` child job per selected tab. Selection is explicit — there is no default. (The ad-hoc `--tabs`/`--all` kind and the plan path are two doors to one task; the ad-hoc kind retires once nothing submits it.) Keeping a league up to date is the plan path: `acq policy set` once, then `--plan` and `--apply` until the plan says nothing to do — a map or unique tab's substashes are known only once the tab is fetched, so a first sync takes two rounds, and each apply ends by saying what is left

Usage: acq refresh [OPTIONS]

Options:
      --all
          Every tab in the league (folder children included, folders not)

      --tabs <TABS>
          Comma-separated tab ids

      --deep
          Also follow map/unique substashes (per tab, as child jobs)

      --plan[=<FILE>]
          Compile the stored sync policy (`acq policy`) into the explicit action set and print it — nothing is submitted or sent. A running daemon adds its read-only quote. With --json, prints the serializable plan envelope. `--plan=FILE` (or `=-` for stdin) renders a reviewed envelope instead, through the same renderer, with the quote it carries

      --expand
          With --plan: one line per action and every quote note, instead of the grouped view (groups over ten entities are counted)

      --apply[=<FILE>]
          Execute the plan: exactly its actions, as one `apply` parent job that never expands the set. Bare `--apply` compiles the stored policy now, so it never fetches what is fresh; `--apply=FILE` (or `--apply=-` for stdin) reads a reviewed plan envelope from `refresh --plan --json`. A plan spends each request once: a target fetched after the plan was compiled, or a request the daemon already holds, is named and not sent again, so applying a file twice, or retrying an apply that is still running, sends nothing (`applied: false` and `spent` in JSON, exit 0). To fetch what is fresh, name it: `acq stash`, `acq character`, `refresh --tabs`. Refused if the stored policy revision no longer matches the plan's

      --max-requests <MAX_REQUESTS>
          Refuse the apply before anything runs if the plan authorizes more than this many requests (checked by the daemon at admission, before any child job exists)

      --league <LEAGUE>
          Defaults to Standard. With `--apply=FILE`, the plan's own league governs; giving --league too asserts they agree

      --realm <REALM>
          pc (default), xbox, sony, or poe2 (a poe2 policy entry can cover characters only). With `--apply=FILE`, the plan's own realm governs; giving --realm too asserts they agree

  -h, --help
          Print help (see a summary with '-h')

Reading a plan as an agent: the text is a function of the envelope, so count with `jq` over `acq refresh --plan --json` rather than parsing prose —
  jq '.logical_requests'
  jq '[.actions[] | .action] | group_by(.) | map({(.[0]): length}) | add'          # requests by kind
  jq '[.actions[] | select(.action == "fetch_substash") | .parent] | group_by(.) | map({(.[0]): length}) | add'   # substashes per parent
  jq '[.skipped_tabs[], .skipped_characters[] | .reason.kind] | group_by(.) | map({(.[0]): length}) | add'   # skips by reason
`acq refresh --apply --json` adds `store_changes` beside the outcome; `acq store events --summary --json` is the per-location summary.
```

## `acq policy set`

```text
Write the policy: inline JSON, `-` to read stdin, or `@<path>` to read a file. Validated before it is stored — a typo'd field or an unknown version is refused, never half-honored. Each realm the value names replaces that realm's policy, every league of it; a realm it does not name stays as stored, and a realm named with no leagues (`"poe2":{"leagues":{}}`) is removed. To add a league, read the policy with `acq policy show` and write its realm back with the league added; `--replace` writes the whole policy instead

Usage: acq policy set [OPTIONS] <VALUE>

Arguments:
  <VALUE>
          The policy as JSON, `-` for stdin, or `@<path>` for a file

Options:
      --if-revision <IF_REVISION>
          Only write if the stored policy is at exactly this revision (what `acq policy show` printed when you reviewed it); refused with the current revision otherwise. 0 writes only where no policy is stored yet, and is refused with the stored revision where one is. Without it the write replaces whatever revision is currently stored — though a write racing in between still conflicts rather than being clobbered

      --replace
          Replace the whole policy: every realm the value does not name is removed

  -h, --help
          Print help (see a summary with '-h')

The policy, version 3:
  {"version":3,"realms":{"pc":{"leagues":{"Standard":{"tabs":"all","characters":"all","max_age_seconds":3600}}}}}
  realms            pc, xbox, sony or poe2, each with its leagues by name
  tabs              "all", or a list of tab ids (`acq stashes` or `acq tabs` print them); an id covers
                    the tab, a folder's children and a map or unique tab's substashes; not under poe2
  characters        "all", or a list of character ids (`acq characters`)
  max_age_seconds   required: what is older than this is fetched again; a plan made sooner says nothing to do
A league entry names tabs, characters or both. Nothing is fetched by setting a policy: `acq refresh --plan` shows what it asks for, `acq refresh --apply` fetches it.
```

## `acq jobs`

```text
The live jobs: id, parent, kind, target (from params), state (`↻n` counts 429 re-queues), priority, account, submitter, ETA. Every waiting and running job is listed, and the ten most recent finished ones; the last line counts them all, and says when the next waiting job starts and when the last one does. `--json` is every job the daemon holds. Observes only: with no daemon running it never spawns one, and answers from the ledger on disk instead — the non-terminal rows as the last daemon left them, without ETAs, and how long ago they were written; `--json`: `running: false`, `persisted` (`jobs`, `written_at`; `null` when this shell's world has no queue yet). A job command spawns a successor that restores them; `cancel` then acts on them

Usage: acq jobs [OPTIONS]

Options:
      --watch              Subscribe, print the queue, then every job-state change as it happens; the queue is printed again after a missed-events signal, and the watch ends when the daemon stops
      --all                List every finished job the daemon still holds, not the ten most recent. A daemon holds the jobs it ran: an earlier daemon's finished jobs are not listed, and `acq result <id>` still answers them from disk
  -h, --help               Print help
```

## `acq result`

```text
A finished job's payload or error. Kept on disk (7 days done, 30 failed, by default) and answered whether or not a daemon runs; a job still waiting or running is an error unless --wait. A failed or cancelled job exits 1. A failed fetch's refused body is in `acq store refused <id>`, not here

Usage: acq result [OPTIONS] <ID>

Arguments:
  <ID>

Options:
      --wait               Block until the job finishes, printing progress on stderr, then print the result: how a `--detach`ed job is collected. Needs the daemon that is running the job
  -h, --help               Print help
```
